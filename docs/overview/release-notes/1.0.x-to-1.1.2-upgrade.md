# Upgrade from other 1.0.x releases to 1.1.2

The [1.0.1 to 1.1.2 upgrade](./1.0.1-to-1.1.2-upgrade.md) is the complete
procedure. This page lists what is different when you start from another 1.0.x
release, so you can follow that guide with the changes below.

| Starting point | Covered here |
| --- | --- |
| Control plane 1.0.0 | Yes |
| Control plane 1.0.1 | Yes, no differences (use the 1.0.1 guide as written) |
| Control plane 1.0.3 | Yes, one difference |
| Control plane 1.0.2 and 1.0.4 through 1.0.8 | Not yet. See [Releases not covered yet](#releases-not-covered-yet). |
| Compute plane 1.0.0 through 1.0.4 | Yes. See [Compute plane](#compute-plane). |

The target is the same as in the 1.0.1 guide: control plane 1.1.2 and compute
plane 1.1.0. Upgrade the control plane first, then each GPU cluster.

## Find your starting release

The upgrade receipt is not a reliable way to tell 1.0.x releases apart, because
several of them record the same version. Use the installed chart versions. With
the session from [Step 1](./1.0.1-to-1.1.2-upgrade.md#step-1-set-up-the-session)
of the 1.0.1 guide:

```bash
helm --kubeconfig "$CONTROL_KUBECONFIG" list -A -o json \
  | jq -r '.[] | select(.name == "api" or .name == "ingress" or .name == "upgrade-receipt") | "\(.name)\t\(.chart)"'
```

| `api` chart | `ingress` chart | `upgrade-receipt` release | Starting release |
| --- | --- | --- | --- |
| `helm-nvcf-api-1.27.1` | `nvcf-gateway-routes-1.18.2` | not listed | 1.0.0 |
| `helm-nvcf-api-1.27.1` | `nvcf-gateway-routes-1.18.2` | listed | 1.0.1 or 1.0.3 |
| Any other `api` chart, or `ingress` 1.18.3 | | | 1.0.2 or later. See [Releases not covered yet](#releases-not-covered-yet). |

Releases 1.0.1 and 1.0.3 pin the same charts and run the same images, so you do
not need to tell them apart.

## Control plane

### Starting from 1.0.1

Nothing changes. Follow the [1.0.1 guide](./1.0.1-to-1.1.2-upgrade.md) as
written. The hostname policy step is required, because your `ingress` chart is
1.18.2.

### Starting from 1.0.3

Follow the 1.0.1 guide as written. The only difference is that 1.0.3 added
operator settings for the NATS images and pod security context:

- `nats.container.image.registry`, `nats.container.image.repository` and
  `nats.container.image.tag`
- `nats.natsBox.container.image.registry`, `nats.natsBox.container.image.repository`
  and `nats.natsBox.container.image.tag`
- `nats.podTemplate.merge.spec.securityContext` and
  `nats.natsBox.podTemplate.merge.spec.securityContext`

1.1.2 reads all of these keys, so carry any you set into the new environment file
in [Step 3](./1.0.1-to-1.1.2-upgrade.md#step-3-decide-the-ha-mode-and-prepare-configuration).
They appear as `+` lines in `control-overrides.diff`. The defaults are unchanged,
so if you set none of them there is nothing to do.

### Starting from 1.0.0

Follow the 1.0.1 guide with these two changes.

1. **There is no upgrade receipt yet.** 1.0.0 has no `upgrade-receipt` release, so
   this upgrade writes the first one.
   - In [Step 4](./1.0.1-to-1.1.2-upgrade.md#step-4-check-the-starting-state-and-take-backups),
     the command that saves `receipt-before.yaml` finds nothing and leaves the
     file empty. That is expected.
   - [Step 13](./1.0.1-to-1.1.2-upgrade.md#step-13-write-the-upgrade-receipt)
     creates the receipt. Its helper job uses a public image,
     `docker.io/alpine/k8s:1.33.1`, which does not follow `global.image`. Check
     that your cluster can pull it before you start:

     ```bash
     docker manifest inspect docker.io/alpine/k8s:1.33.1 > /dev/null && echo "reachable"
     ```

     To use a mirror instead, set `upgradeReceipt.image.registry` and
     `upgradeReceipt.image.repository` together in your environment file.

1. **LLM add-on only: the default Pylon discovery endpoint changes.** If
   `addons.llm.enabled` is `true` and you have not set
   `global.workerEndpoints.llmRequestRouterAddress`, the default changes from
   `llm-request-router.nvcf.svc.cluster.local:50071` to
   `llm-request-router-backend-router.nvcf.svc.cluster.local:50071`. The new
   default applies when backend routing is enabled, which follows
   `addons.llm.enabled`. To keep the old endpoint, set
   `global.workerEndpoints.llmRequestRouterAddress` explicitly before you apply.

The hostname policy step is required for 1.0.0, because its `ingress` chart is
1.18.2.

## Compute plane

Every 1.0.x compute-plane stack pins the same `nvca-operator` chart, 1.28.0.
Compute plane 1.1.0 moves it to 1.37.1. What differs is the NVCA agent and the
images the stack pins. The package `VERSION` file does not identify the release
(1.0.0 has none, and 1.0.2 through 1.0.4 all report `1.0.0`), so read the values
from the package you installed:

```bash
grep -nE 'nvcaVersion|sharedStorage|imageCredHelper|byooOtelCollector' -A1 \
  "$OLD_COMPUTE_STACK/environments/base.yaml"
```

Match the NVCA version and the image tags it prints against the table.

| Setting | 1.0.0 | 1.0.1 | 1.0.2 | 1.0.3 | 1.0.4 | 1.1.0 |
| --- | --- | --- | --- | --- | --- | --- |
| NVCA agent (`nvcaVersion`) | 3.10.0 | 3.10.3 | 3.10.3 | 3.10.3 | 3.10.3 | 3.18.6 |
| Image credential helper (`imageCredHelper.imageTag`) | chart default | 0.11.3 | 0.11.3 | 0.11.3 | 0.11.3 | 0.11.4 |
| Shared storage image (`sharedStorage.imageTag`) | chart default | chart default | chart default | 1.0.8 | 1.0.9 | 1.0.9 |
| Collector image tag | 0.157.0-nv-0.2.1 | 0.157.0-nv-0.2.1 | 0.160.0-nv-0.2.8 | 0.160.0-nv-0.2.9 | 0.160.0-nv-0.2.9 | 0.160.0-nv-0.4.7 |

The `byooOtelCollector` setting first appears in 1.0.2, and `sharedStorage` in
1.0.3. If you start from an earlier release, these keys are new to your
environment file.

Follow [Step 15](./1.0.1-to-1.1.2-upgrade.md#step-15-upgrade-each-compute-cluster)
of the 1.0.1 guide, with these points:

- Your 1.0.x environment file may already pin some of these values. Step 15 has
  you copy only your own changes from the old environment file into the new one,
  so do not carry old `nvcaVersion` or image tags over the 1.1.0 defaults.
- The new defaults need images your registry may not have yet. Run the image
  listing in Step 15 and mirror every image it shows before you apply.
- Keep the cluster's existing registration. Do not run `register-cluster` again.

## Releases not covered yet

Control plane 1.0.2 and 1.0.4 through 1.0.8 are not covered by this guide yet.
Those releases include newer builds of several components than 1.1.2 does, so
upgrading straight to 1.1.2 would move those components to older builds. Do not
upgrade from these releases to 1.1.2 until guidance for them is published. Check
the [compatibility matrix](../compatibility-matrix.md) and the release notes for
a 1.1 release that carries those builds.
