# Upgrade from NVCF 1.0.x to NVCF 1.1.0

This guide upgrades a running NVCF deployment from an NVCF 1.0.x edition to
NVCF 1.1.0. NVCF 1.1.0 selects Self-Managed 1.1.4 for the control plane,
Compute Plane 1.1.0 for each GPU cluster, and Observability 1.0.0. Every step
has commands you can copy and run. Read the whole guide, including
[Find your starting point](#find-your-starting-point) and
[What changes](#what-changes), before you start.

| NVCF edition | Self-Managed | Compute Plane | Observability | Covered |
| --- | --- | --- | --- | --- |
| 1.0.0, 1.0.1, 1.0.2, 1.0.3 | 1.0.1 | 1.0.0 | 1.0.0 | Yes |
| 1.0.4 | 1.0.10 | 1.0.5 | 1.0.0 | No, see [Releases not covered yet](#releases-not-covered-yet) |
| 1.1.0 (target) | 1.1.4 | 1.1.0 | 1.0.0 | |

Stacks release independently, so a deployment can also run a Self-Managed or
Compute Plane patch release that no edition selects. The stack releases this
guide covers are:

| Stack | Source | Target | Target tag |
| --- | --- | --- | --- |
| Self-Managed (control plane) | 1.0.0 through 1.0.8 | 1.1.4 | `deploy/stacks/self-managed/v1.1.4` |
| Compute Plane | 1.0.0 through 1.0.4 | 1.1.0 | `deploy/stacks/nvcf-compute-plane/v1.1.0` |
| Observability | 1.0.0 | 1.0.0 (unchanged) | `deploy/stacks/observability/v1.0.0` |

## Cross-stack upgrade order

These declarations apply to the supported starting releases in this guide:

| Transition | Required peer |
| --- | --- |
| Compute Plane 1.1.0 | Self-Managed 1.1.0 or later, subject to the compatibility and maintenance policy |
| Self-Managed 1.1.4 during the upgrade window | Existing Compute Plane 1.0.0 can remain until its upgrade |

After the prerequisite NVCA patch below, upgrade the control plane first,
then each GPU cluster to Compute Plane 1.1.0.

Starting from 0.6.x? Complete the
[0.6.2 to 1.0.1 upgrade](./0.6.1-to-1.0.1-upgrade.md) first. Do not skip its
schema or backfill stops.

<Warning>
Do not use this guide to upgrade from NVCF 1.0.4, control plane 1.0.9 or
1.0.10, or compute plane 1.0.5 or 1.0.6. Each of those releases carries a newer build of at
least one component than the 1.1.4 and 1.1.0 stacks pin, so the upgrade would
move that component backwards. See
[Releases not covered yet](#releases-not-covered-yet) before you do anything
else.
</Warning>

## Find your starting point

Commands and package renders were checked using 1.0.1 as the baseline. Every
starting release was also compared with 1.1.4 using its published stack
inventory. The complete upgrade to 1.1.4 still needs live validation.
Release-specific callouts come from the published stack tags and inventories.

The upgrade receipt does not tell 1.0.x releases apart, because most of them
record the same version. Identify your release from the installed chart
versions instead. [Set up the session](#set-up-the-session) sets `CONTROL_KUBECONFIG`; you can set it yourself to
run this now:

```bash
helm --kubeconfig "$CONTROL_KUBECONFIG" list -A -o json \
  | jq -r '.[] | select(.name == "api" or .name == "ingress" or .name == "upgrade-receipt" or .name == "cassandra") | "\(.name)\t\(.chart)"'
```

| `api` chart | `ingress` chart | `cassandra` chart | `upgrade-receipt` release | Your release | Covered |
| --- | --- | --- | --- | --- | --- |
| `helm-nvcf-api-1.27.1` | `nvcf-gateway-routes-1.18.2` | `helm-nvcf-cassandra-0.21.3` | not listed | 1.0.0 | Yes |
| `helm-nvcf-api-1.27.1` | `nvcf-gateway-routes-1.18.2` | `helm-nvcf-cassandra-0.21.3` | listed | 1.0.1 or 1.0.3 | Yes |
| `helm-nvcf-api-1.27.2` | `nvcf-gateway-routes-1.18.3` | `helm-nvcf-cassandra-0.21.3` | listed | 1.0.2 or 1.0.4 through 1.0.6 | Yes |
| `helm-nvcf-api-1.27.4` | `nvcf-gateway-routes-1.18.3` | `helm-nvcf-cassandra-0.21.3` | listed | 1.0.7 | Yes |
| `helm-nvcf-api-1.27.5` | `nvcf-gateway-routes-1.18.3` | `helm-nvcf-cassandra-0.21.3` | listed | 1.0.8 or 1.0.9 | 1.0.8 yes; 1.0.9 [not covered yet](#releases-not-covered-yet) |
| `helm-nvcf-api-1.27.5` | `nvcf-gateway-routes-1.18.3` | `helm-nvcf-cassandra-0.21.4` | listed | 1.0.10 | [No, not covered yet](#releases-not-covered-yet) |

If your charts match none of these rows, stop: your deployment is not one of the
published 1.0.x releases.

Charts alone do not separate 1.0.8 from 1.0.9, because they pin the same charts.
They differ in the NATS images. List them:

```bash
kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n nats-system get pods \
  -o jsonpath='{range .items[*]}{range .spec.containers[*]}{.image}{"\n"}{end}{end}' | sort -u
```

Release 1.0.8 runs `docker.io/synadia/nats-server:2.14.6-alpine3.22` and
`docker.io/natsio/nats-server-config-reloader:0.24.0`. Release 1.0.9 runs
`nats-server:2.14.9-alpine3.22` and `nats-server-config-reloader:0.25.0`.

Releases that pin the same chart and image versions need no separate handling:

- 1.0.0, 1.0.1 and 1.0.3 pin the same charts and images. Only 1.0.0 lacks the
  upgrade receipt.
- 1.0.4, 1.0.5 and 1.0.6 pin the same charts and images.
- 1.0.2 has a source tag but no GitHub release or inventory. Its image and chart
  pins in `environments/base.yaml` match 1.0.4, so follow the 1.0.4 column.

What differs by starting release:

| Where | 1.0.0 | 1.0.1 or 1.0.3 | 1.0.2, 1.0.4 to 1.0.6 | 1.0.7 | 1.0.8 |
| --- | --- | --- | --- | --- | --- |
| [Decide the HA mode and prepare configuration](#decide-the-ha-mode-and-prepare-configuration) | Add: LLM add-on endpoint default changes; NATS images move to public registries | Add: NATS images move to public registries; 1.0.3 also carries NATS settings | Add: carry NATS settings; nats-box moves to a public registry | Same as 1.0.4 | Same as 1.0.4 |

| [Replace the OpenBao pods](#replace-the-openbao-pods) | Replace the pods (2.6.2 to 2.6.3) | Replace the pods | Replace the pods | Replace the pods | Skip: already on `2.6.3-nv-1.3.7` |

[Compute plane](#compute-plane).

### Releases not covered yet

Do not upgrade control plane 1.0.9 or 1.0.10, or compute plane 1.0.5 or 1.0.6, to
the 1.1.4 and 1.1.0 stacks yet. Each carries a newer build of some components
than the target pins. Starting from 1.0.8 or earlier moves nothing backwards.

| Component | 1.0.9 | 1.0.10 | 1.1.4 |
| --- | --- | --- | --- |
| NATS server image | 2.14.9-alpine3.22 | 2.14.9-alpine3.22 | 2.14.6-alpine3.22 |
| NATS config reloader image | 0.25.0 | 0.25.0 | 0.24.0 |
| cert-manager images (five) | v1.20.2 | v1.20.5 | v1.20.2 |
| `cert-manager` chart | 0.1.0 | 0.2.0 | 0.1.0 |
| OpenBao server image | 2.6.3-nv-1.3.7 | 2.6.3-nv-1.3.9 | 2.6.3-nv-1.3.7 |

Only the rows where 1.1.4 is older apply to each release: 1.0.9 has the first
two, and 1.0.10 has all of them. Compute plane 1.0.5 and 1.0.6 pin
`nats-server-config-reloader` 0.25.0, and compute plane 1.1.0 pins 0.24.0.

Self-Managed 1.0.10 also uses the OpenBao JWT plugin lifecycle (`bridge` and
`versioned` modes, chart `jwtPluginLifecycle`), which first appears in OpenBao
chart 0.32.9. The OpenBao chart that 1.1.4 selects (0.36.1) does not have it.
Do not replace the bridge image or clear stored plugin version pins to force
this upgrade.

Do not carry these image pins forward into a 1.1.4 environment file: they are
builds from the 1.0 line, and the 1.1.4 defaults are the qualified set. Wait
for guidance for your release, and check the
[compatibility matrix](../compatibility-matrix.md) and the release notes.

<Warning>
Do not run a whole-stack `make apply` or `helmfile sync` first. The control
plane has stops that must happen in order: hostname policy, dependencies and
migrations, OpenBao pod replacement, core services, then Cassandra replication
for high availability. Highly available (HA) mode is on by default in 1.1.4.
Decide your mode in [Decide the HA mode and prepare configuration](#decide-the-ha-mode-and-prepare-configuration)
before you apply anything.
</Warning>

### Control plane: behavior that changes

| Area | What happens on upgrade | What you do |
| --- | --- | --- |
| High availability | `highAvailability.mode` is new and defaults to `preferred`. An environment file that does not set it activates HA: replica-safe services scale to 2, Cassandra and NATS scale to 3 members, and PodDisruptionBudgets and placement rules apply. | Choose `none`, `preferred` or `enforced` in [Decide the HA mode and prepare configuration](#decide-the-ha-mode-and-prepare-configuration). |
| Cassandra | The chart adds a config setting (`range_request_timeout: 5000ms`) and the server image moves to `5.0.9-nv-2.0.7`. The pod template changes, so the StatefulSet restarts its pods one at a time. The migrations image moves to `nvcf-cassandra-migrations:0.19.4`, whose new migrations only add schema ([Apply the dependency stage](#apply-the-dependency-stage)). | Plan a short Cassandra interruption if you run a single member. |
| OpenBao | Server image `2.6.2-nv-1.3.4` (releases through 1.0.7) becomes `2.6.3-nv-1.3.7`; 1.0.8 already runs it. The migrations image used by the server hooks moves to 0.23.1. The StatefulSet uses `OnDelete`, so Helm success does not replace the running pods. | Replace the pods yourself in [Replace the OpenBao pods](#replace-the-openbao-pods), unless you start from 1.0.8. |
| Gateway hostname policy | The 1.0.0, 1.0.1 and 1.0.3 gateway-routes chart (1.18.2) has an older hostname policy that blocks the new admin issuer route patch. 1.18.3 carries the corrected policy. | Run the one-time `apply-hostname-policy` step ([Refresh the hostname policy](#3-refresh-the-hostname-policy)). |
| Event Ledger | New release `event-ledger`, on by default (`addons.eventLedger.enabled: true`). It uses the existing `event_ledger` keyspace, and its OpenBao setup runs in the OpenBao migrations job. | Keep it on, or set `addons.eventLedger.enabled: false` before you apply. |
| NATS worker authentication | New `nats.workerAuth` setting. The default, `nkey`, keeps today's behavior. | Nothing, unless you switch to `token`. See "Worker NATS Authentication" in [control-plane operations](../../self-managed/control-plane-operations.md). |
| Admin issuer proxy | Now optional (`adminIssuerProxy.enabled`), still on by default. | Nothing, unless you want to disable it. |
| NVCT remote config | New `nvctApi.remoteConfig`, empty by default. | Nothing. |
| Upgrade receipt | The final stage records the installed stack version in `nvcf-upgrade-receipt`. | Validate package stamps first, then compare the receipt with the selected release. |
| NATS images | The NATS server and nats-box images default to public registries (`docker.io/synadia/nats-server`, `docker.io/natsio/nats-box:0.20.1-nonroot`), and the config reloader to `docker.io/natsio/nats-server-config-reloader`. Releases 1.0.0, 1.0.1 and 1.0.3 pulled the server and nats-box from the NVCF catalog; 1.0.2 and 1.0.4 through 1.0.8 pulled the server from `docker.io` and nats-box from the catalog. | If your cluster cannot pull from public registries, set the registry and repository for all three images to your mirror in [Decide the HA mode and prepare configuration](#decide-the-ha-mode-and-prepare-configuration). |
| Worker sidecars | API and NVCT remote config pin the ESS agent sidecar image to `ess-agent:1.4.4`. Running functions keep the images they started with. | If you mirror sidecar images, mirror `ess-agent:1.4.4`. |
| LLM add-on image tags | With `addons.llm.enabled`, the request router and Pylon tag must match, and `addons.llm.requestRouter.image.tag` is now required. `base.yaml` sets `0.29.2`. | Keep the default unless you mirror or pin it. |

The package `VERSION` file does not identify your compute release: 1.0.0 has
none, and 1.0.2 through 1.0.4 all report `1.0.0`. Read the values from the
package you installed and match them against the table:

```bash
grep -nE 'nvcaVersion|sharedStorage|imageCredHelper|byooOtelCollector' -A1 \
  "$OLD_COMPUTE_STACK/environments/base.yaml"
```

The `byooOtelCollector` setting first appears in 1.0.2 and `sharedStorage` in
1.0.3, so if you start from an earlier release those keys are new to your

for TLS worker callbacks), `byoo.*` sidecar resources, `utils.resources`,
`byooFluentBit` and `eventLedgerServiceURL`. Dynamo, Grove and KAI Scheduler
pins are unchanged. Running function pods keep the worker images they started
with; the new defaults apply to deployments created or replaced afterwards.

## Known issues

- Historical packages can retain the train version `1.1.0` instead of the
  selected patch `1.1.4`. The package and receipt checks above reject this
  mismatch. Obtain a correctly stamped, qualified package before maintenance.
- Only 1.0.1 had command and render checks. Releases 1.0.0, 1.0.2, 1.0.3 and
  1.0.4 through 1.0.8 are covered from published tags and inventories and were
  not rehearsed, including skipping [Refresh the hostname policy](#3-refresh-the-hostname-policy) and [Replace the OpenBao pods](#replace-the-openbao-pods) where
  [Find your starting point](#find-your-starting-point) says to. Releases 1.0.9
  and 1.0.10 are not covered; see
  [Releases not covered yet](#releases-not-covered-yet).
- A single-member OpenBao installation is not covered; see
  [Replace the OpenBao pods](#replace-the-openbao-pods).
- Whether Compute Plane 1.0.0 through 1.0.4 keep working against Self-Managed
  1.1.4 during the upgrade window was not checked live.

## Before starting

1. Schedule a maintenance window. You will pause new function invocations and
   task submissions, and a single-member Cassandra restarts once.
1. You need an operator workstation with `kubectl`, `helm` 3.12 or later,
   `helmfile` 1.1.x (not 1.2.x), the `helm-diff` plugin 3.11 or later, `jq`,
   `curl`, Mike Farah's `yq` v4, and `ngc` if you download packages from NGC.
   Helmfile 1.2.0 removed sequential execution, which these stacks need. See
   [required tools](../../self-managed/helmfile-installation.md#required-tools-and-software).
1. Keep your existing control-plane and compute-plane directories, your
   `environments/<environment-name>.yaml`, your
   `secrets/<environment-name>-secrets.yaml`, and the registration file for each
   GPU cluster (`<cluster-name>-register-values.yaml`). The upgrade reuses each
   cluster's registration. Do not run `register-cluster` again.
1. Choose canary workloads: one serving function, one function that reads a
   secret, and one running task. You will test them before and after.
1. If you mirror images and charts to a private registry, mirror the 1.1.4
   artifacts first. [Get the 1.1.4 packages and check artifacts](#get-the-114-packages-and-check-artifacts) checks availability.
1. Before NATS restarts in [Apply the dependency stage](#apply-the-dependency-stage), patch every compute cluster running NVCA
   3.10.0 through 3.10.2 to a compatible 3.10.3 or later 3.10 patch. Preserve
   registration; see [NATS recovery](../../self-managed/upgrade-recovery.md#deployments-stuck-after-a-nats-restart).
   The Compute Plane 1.1.0 upgrade still waits until [Upgrade each compute cluster](#7-upgrade-each-compute-cluster).

## 1. Set deployment values

### Set up the session

Download this read-only script into one directory. [Check the starting state](#check-the-starting-state) and [Render and review the changes](#render-and-review-the-changes) use it to
stop an upgrade that would move an image to an older version:

<Download src="../../../fern/assets/upgrade-checks/check-upgrade-image-moves.py" filename="check-upgrade-image-moves.py">Image move check</Download>

Use a dedicated shell. Replace every value in angle brackets. Run this block
first, and again after any shell restart.

```bash
bash
set -euo pipefail
umask 077

export WORKDIR="$HOME/nvcf-upgrade-1.1.4"
export UPGRADE_SCRIPTS="/absolute/path/to/downloaded-scripts"
export OLD_CONTROL_STACK="/absolute/path/to/existing/nvcf-self-managed-stack"
export OLD_COMPUTE_STACK="/absolute/path/to/existing/nvcf-compute-plane-stack"
export HELMFILE_ENV="<environment-name>"
export CONTROL_CONTEXT="<control-plane-kube-context>"
export BACKUP_DIR="$WORKDIR/backup"
mkdir -p "$WORKDIR" "$BACKUP_DIR"

# One kubeconfig per cluster, so a stray context switch cannot redirect a command.
export CONTROL_KUBECONFIG="$WORKDIR/control.kubeconfig"
kubectl config view --minify --flatten --raw --context "$CONTROL_CONTEXT" > "$CONTROL_KUBECONFIG"

kc() { kubectl --kubeconfig "$CONTROL_KUBECONFIG" "$@"; }
control_helmfile() {
  (cd "$CONTROL_STACK" && HELMFILE_ENV="$HELMFILE_ENV" \
    helmfile --environment default --kubeconfig "$CONTROL_KUBECONFIG" "$@")
}
wait_workloads() {
  local kubeconfig="$1" namespace="$2" workload strategy
  kubectl --kubeconfig "$kubeconfig" -n "$namespace" get deployments,statefulsets -o name |
    while IFS= read -r workload; do
      strategy=$(kubectl --kubeconfig "$kubeconfig" -n "$namespace" \
        get "$workload" -o jsonpath='{.spec.updateStrategy.type}')
      if [ "$strategy" = "OnDelete" ]; then
        printf '%s uses OnDelete; replace its pods with the procedure in this guide\n' "$workload"
        continue
      fi
      kubectl --kubeconfig "$kubeconfig" -n "$namespace" rollout status "$workload" --timeout=15m
    done
  kubectl --kubeconfig "$kubeconfig" -n "$namespace" get pods
}
declare -f kc control_helmfile wait_workloads > "$WORKDIR/helpers.sh"
declare -p WORKDIR UPGRADE_SCRIPTS OLD_CONTROL_STACK OLD_COMPUTE_STACK HELMFILE_ENV \
  CONTROL_CONTEXT BACKUP_DIR CONTROL_KUBECONFIG > "$WORKDIR/session.sh"

kc config current-context
kc get nodes
```

All nodes must be `Ready`. To resume later, start a new `bash`, run
`set -euo pipefail`, set `WORKDIR` to the directory you used above
(`export WORKDIR="$HOME/nvcf-upgrade-1.1.4"`), then

### Decide the HA mode and prepare configuration

#### Choose the HA mode

| Mode | Result | Needs |
| --- | --- | --- |
| `none` | Keeps your current footprint: no extra replicas, no new PodDisruptionBudgets. | Nothing. |
| `preferred` (default) | Replica-safe services run 2 replicas. Cassandra, NATS and OpenBao run 3 members with soft anti-affinity and zone spread. Pods still schedule when capacity is short. | At least 3 schedulable nodes. |
| `enforced` | Same sizing with hard placement. Pods stay `Pending` rather than co-locate. | At least 3 nodes, 3 zones with capacity, `topology.kubernetes.io/zone` labels, and a `WaitForFirstConsumer` StorageClass. |

If this is a single-node cluster, or you are not ready to add capacity, choose
`none`. You can move to HA later with the same procedure. The full behavior,
including zone spread, is in the [high availability guide](../../self-managed/high-availability.md).

Check what your cluster offers:

```bash
kc get nodes -L topology.kubernetes.io/zone
kc get storageclass
kc get nodes --no-headers | wc -l
```

For `enforced`, the StorageClass your Cassandra, NATS and OpenBao volumes use
must show `WaitForFirstConsumer` as its volume binding mode. Replica-safe
services roll with `maxUnavailable: 0` and `maxSurge: 1`, so leave room for one
extra pod per service.

- `nats.container.image.registry`, `nats.container.image.repository` and
  `nats.container.image.tag`
- `nats.natsBox.container.image.registry`,
  `nats.natsBox.container.image.repository` and

`docker.io/natsio/nats-box` and `docker.io/natsio/nats-server-config-reloader`).

## 4. Drain pending work

Stop new production requests and task submissions at their callers. NATS
request queues use memory storage, and the dependency stage can restart NATS.
Wait for queued work to finish; do not cancel it to get an empty queue.

For every affected function and version, use a key with `queue_details` scope
(`NVCF_API_KEY`). The task command below uses a separate key with `list_tasks`
scope (`NVCF_NVCT_API_KEY`) and your Tasks endpoint (`base_nvct_url` and
`nvct_host` in the CLI configuration). Verify both with the
[CLI authentication settings](../cli.md) before you start:

```bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function queue status "$FUNCTION_ID" "$VERSION_ID"
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" task list --status RUNNING
```

tasks. Then check the control plane's own single-replica memory streams on every
NATS server, through the monitoring port 8222:

```bash

  select(any(.spec.containers[]; .name == "nats")) | .metadata.name')

      > "$NATS_DRAIN_DIR/$pod.log" 2>&1 &
    forward_pid=$!
    trap 'kill "$forward_pid" 2>/dev/null || true; wait "$forward_pid" 2>/dev/null || true' EXIT
    for attempt in {1..30}; do
      kill -0 "$forward_pid"
      grep -q 'Forwarding from 127.0.0.1:' "$NATS_DRAIN_DIR/$pod.log" && break
      sleep 1
    done
    grep -q 'Forwarding from 127.0.0.1:' "$NATS_DRAIN_DIR/$pod.log"
    curl --fail --silent --show-error --connect-timeout 5 --max-time 30 \
      "http://127.0.0.1:$NATS_MONITOR_PORT/jsz?accounts=true&streams=true&config=true" \
      > "$NATS_DRAIN_DIR/$pod.json"
    jq -e '.account_details | type == "array"' "$NATS_DRAIN_DIR/$pod.json"
    jq -e 'all(.account_details[];
      ((.stream_detail // []) | type == "array") and
      all((.stream_detail // [])[];
        (.config.storage | type == "string") and
        (.state.messages | type == "number")))' "$NATS_DRAIN_DIR/$pod.json"
  )
done
jq -se '[.[] | .account_details[]? | .stream_detail[]? |
  select(.config.storage == "memory" and (.config.num_replicas // 1) == 1) |
  {name: .name, messages: .state.messages}] |
  if length > 0 and all(.[]; .messages == 0)
  then . else error("Memory streams missing or not drained; do not roll NATS") end' \
  "$NATS_DRAIN_DIR/"*.json
```

Every single-replica memory stream must show zero messages. A failed or
slow read, a missing stream or a nonzero count blocks the upgrade. A server whose
accounts hold no streams reports no stream details, which counts as empty; the
final check still requires at least one single-replica memory stream. Each attempt writes to a new directory, so files from an
earlier attempt cannot satisfy the check. Wait for the work to drain
and repeat; do not discard messages. If your NATS monitoring is configured
differently, use its endpoint and keep the same per-server check.
For retained creation messages or stuck deployments, follow the
[recovery steps](../../self-managed/upgrade-recovery.md#inspect-retained-creation-messages)
before proceeding.

### Apply the dependency stage

This stage updates Cassandra, NATS, cert-manager, OpenBao and the PKI. Review



What you will see:

- Cassandra restarts one pod at a time because of the config change and the
  new server image (2.0.7), and grows to 3 members under `preferred` or
  `enforced`. A single-member cluster is unavailable while its one pod restarts.
- Migrations run as Helm hook jobs. They must complete successfully. The
  Cassandra migrations image moves to 0.19.4 from 0.17.6 (releases 1.0.0, 1.0.1
  and 1.0.3) or 0.17.7 (1.0.2 and 1.0.4 through 1.0.8). The two source images
  apply the same CQL, so the following applies to every supported release. The
  new migrations only add schema: nullable columns on `sis_api.requests`,
  `sis_api.instances` and the `event_ledger` tables, and indexes on the new
  `sis_api` `creation_bucket` column. They drop nothing. Existing rows keep
  null in the new columns, and nothing backfills them. Building the indexes
  reads the existing rows, so a large `sis_api` table can make that job run
  longer.
- The OpenBao hooks (image 0.23.1) refresh the service, admin issuer and Event
  Ledger configuration, and add a signing role for gRPC proxy events. They
  only add or merge configuration and keep existing roles.
- OpenBao shows the new template, but its pods still run the old image
  until [Replace the OpenBao pods](#replace-the-openbao-pods). `wait_workloads` reports it as `OnDelete`. If you start from
  1.0.8 the image does not change, so [Replace the OpenBao pods](#replace-the-openbao-pods) has nothing to replace.

```bash

kc -n cassandra-system get jobs
kc -n vault-system get jobs
```

Investigate any failed job before continuing; do not disable hooks.

### Replace the OpenBao pods

The OpenBao StatefulSet uses `OnDelete`: Helm updated its template, but the
running pods keep their old image. If you start from 1.0.8, the members already
run `nvcf-openbao:2.6.3-nv-1.3.7`, the image this step installs. Run only the
verification at the end of this step, then continue to [Apply the core services](#apply-the-core-services). Replace them one at a time, standbys first.
Never delete a persistent volume claim, reinitialize OpenBao, or replace more
than one member at once. This procedure is the 2.6.2 to 2.6.3 patch procedure
from the [OpenBao patch upgrade runbook](../../self-managed/runbooks/openbao-patch-upgrade.md).
Use that runbook if a step fails or if you customized plugin registration,
policies or PKI.

This procedure is written for the supported OpenBao deployment, a Raft cluster
of several members. Replace a standby first so that leadership does not move
twice. Check the member count:

```bash
kc -n vault-system get statefulset openbao-server -o jsonpath='{.spec.replicas}{"\n"}'
```

If it prints `1`, stop. A single-member OpenBao is not a supported deployment and
this guide has no procedure for it: there is no standby to replace first and no
leadership handover, and OpenBao is unavailable while its one pod restarts and
unseals. Do not continue on your own. Confirm the Raft snapshot from the backup
step and use the
[OpenBao patch upgrade runbook](../../self-managed/runbooks/openbao-patch-upgrade.md)
to plan the change with your NVCF contact.

Confirm the new template and the update strategy:

```bash
kc -n vault-system get statefulset openbao-server \
  -o jsonpath='{range .spec.template.spec.containers[*]}{.name}{": "}{.image}{"\n"}{end}{"updateStrategy: "}{.spec.updateStrategy.type}{"\n"}'
check_openbao
```

The server image must be `nvcf-openbao:2.6.3-nv-1.3.7` and the strategy
`OnDelete`. If either is different, stop. Identify the standbys (the members
that do not report `is_self: true`) and replace one:

```bash

kc -n vault-system wait "pod/$POD" --for=condition=Ready --timeout=5m
check_openbao
```

If the new pod has not appeared yet, wait for it before repeating the wait. The
replacement must report `version: "2.6.3"`, `sealed: false` and the original
`cluster_id`. If it is Ready but still sealed, let auto-unseal finish and run
`check_openbao` again. Repeat for the second standby only after all three
members are healthy.

Then replace the former active member. Transfer leadership first:

```bash
ACTIVE_POD="<current-active-pod-name>"
set -o pipefail
kc -n vault-system get secret openbao-server-root-token -o json |
  jq -er '.data.root_token | @base64d' |
  kc -n vault-system exec -i "$ACTIVE_POD" -c openbao -- sh -ec '
    IFS= read -r BAO_TOKEN
    test -n "$BAO_TOKEN"
    export BAO_TOKEN
    export BAO_ADDR=http://127.0.0.1:8200
    bao operator step-down
  '
check_openbao
```

Wait until a 2.6.3 member reports `is_self: true` and the old active reports
standby. A successful request alone does not confirm the transfer. Then replace
the former active with the same `delete`, `wait`, `check_openbao` sequence. Do
not enable shell tracing or print the token.

Verify all three members and their images:

```bash
check_openbao
kc -n vault-system get pods -l app.kubernetes.io/name=openbao,component=server \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{range .spec.containers[*]}{"  "}{.name}{": "}{.image}{"\n"}{end}{end}'
```

All three must be unsealed on 2.6.3, with one active member and the original
cluster ID. Updating the injector affects only new pods. The services the core
stage rolls in the next step pick up the new agent; roll any other injected
workload through its normal deployment procedure, one service at a time, and
check its authentication and rendered secrets. A single-replica service can be
interrupted during that roll, so never restart all consumers together.

### Raise replication for HA

Skip this step if you chose `highAvailability.mode: none`.

After the dependency stage, Cassandra has 3 members, but your application
keyspaces keep the replication factor they were created with, so losing one
Cassandra node can still make data unavailable. Wait until all three Cassandra
pods are Ready, then raise each keyspace to RF=3 and repair, one member at a
time. The loop below alters only the keyspaces your installation has and skips
the rest. It validates the deployed data-center name against the live database
before any ALTER. Credentials travel over stdin into a temporary protected
[cqlsh credentials file](https://cassandra.apache.org/doc/stable/cassandra/managing/tools/cqlsh.html#credentials).
Do not enable shell tracing.

```bash
CASSANDRA_DC=$(kc -n cassandra-system get statefulset cassandra -o json |
  jq -er '.spec.template.spec.containers[] | select(.name == "cassandra") |
    .env[] | select(.name == "CASSANDRA_DC") | .value')
case "$CASSANDRA_DC" in
  ''|*[!A-Za-z0-9_-]*) echo "Invalid Cassandra data-center name" >&2; exit 1 ;;
esac
read -rs -p "Cassandra administrator password: " CASSANDRA_PASSWORD
printf '\n'
cql() (
  set +x
  printf '%s\n' "$CASSANDRA_PASSWORD" |
    kc -n cassandra-system exec -i cassandra-0 -c cassandra -- sh -ec '
      umask 077
      auth_dir=$(mktemp -d)
      trap '\''rm -rf "$auth_dir"'\'' EXIT
      IFS= read -r password
      printf "[auth_provider]\nmodule = cassandra.auth\nclassname = PlainTextAuthProvider\n" > "$auth_dir/cqlshrc"
      printf "[PlainTextAuthProvider]\nusername = cassandra\npassword = %s\n" "$password" > "$auth_dir/credentials"
      cqlsh --cqlshrc="$auth_dir/cqlshrc" --credentials="$auth_dir/credentials" --no-color -e "$1"
    ' sh "$1"
)
LIVE_DC=$(cql "SELECT JSON data_center FROM system.local;" |
  sed -n '/^[[:space:]]*{/{s/^[[:space:]]*//;p;}' |
  jq -ers 'if length == 1 then .[0].data_center else error("Missing data-center row") end')
test "$LIVE_DC" = "$CASSANDRA_DC"
cql "SELECT keyspace_name, replication FROM system_schema.keyspaces;"
EXISTING_KEYSPACES=$(cql "SELECT keyspace_name FROM system_schema.keyspaces;" | tr -d ' \r')
for ks in nvcf_api nvct_api ess_api api_keys_api sis_api event_ledger nvcf_autoscaler; do
  if printf '%s\n' "$EXISTING_KEYSPACES" | grep -qx "$ks"; then
    cql "ALTER KEYSPACE $ks WITH replication = {'class': 'NetworkTopologyStrategy', '$CASSANDRA_DC': '3'};"
  else
    echo "skipping $ks: not present in this installation"
  fi
done
for pod in cassandra-0 cassandra-1 cassandra-2; do
  kc -n cassandra-system exec "$pod" -c cassandra -- nodetool repair --full
done
unset CASSANDRA_PASSWORD
```

Until the repairs finish, reads at `LOCAL_ONE` can miss rows that exist only on
the original replica. The application keyspaces must now report RF=3 for the validated data center.

JetStream streams are created with the replication factor current at creation
time. The `icms` streams raise themselves to the configured factor when it
starts. Streams created earlier by `nvcf-api` and `invocation-service` stay at
1 replica until you edit them. List them and check:

```bash
kc -n nats-system exec deploy/nats-box -- nats stream report
```

The `Replicas` column lists each member that holds a copy of the stream. A
highly available stream shows three (`nats-0`, `nats-1`, `nats-2`); a stream
created before HA shows one. Raise each stream that shows one:

```bash
STREAM="<stream-name>"
kc -n nats-system exec deploy/nats-box -- nats stream edit "$STREAM" --replicas=3 --force
kc -n nats-system exec deploy/nats-box -- nats stream info "$STREAM"
```

Replace `<stream-name>` with the name from the report, run both commands for
each such stream, and confirm `nats stream info` shows `Replicas: 3`. Use 3, not
2: a 2-replica stream loses quorum when either member is down. The NATS
commands run in the `nats-box` deployment because the `nats` server container
does not include the CLI.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| Render fails with `overrides the highAvailability sizing` | The secrets file sets a replica count that conflicts with the HA sizing. | Remove the override, or set `highAvailability.mode: none`. See [Decide the HA mode and prepare configuration](#decide-the-ha-mode-and-prepare-configuration). |
| `ImagePullBackOff` in a stage | An image is not in your registry or mirror. | Re-run the [Get the 1.1.4 packages and check artifacts](#get-the-114-packages-and-check-artifacts) checks, mirror the missing image, and retry the stage. |
| Pods `Pending` under `enforced` | Fewer than 3 nodes or zones with capacity, or a StorageClass without `WaitForFirstConsumer`. | Add capacity or fix the StorageClass. `preferred` schedules them but does not give zone protection. |
| `apply-hostname-policy` reports the chart still reserves hostnames | The package does not match the selected release. | Recheck the extracted package against [Get the 1.1.4 packages and check artifacts](#get-the-114-packages-and-check-artifacts), then rerun. |
| The admin issuer route patch is denied | The hostname policy step was skipped. | Run [Refresh the hostname policy](#3-refresh-the-hostname-policy), then rerun the core stage. |
| A migration job failed | A dependency was not ready, or a hook could not reach its service. | Read the job logs (`kc -n <namespace> logs job/<name>`), fix the cause, and rerun the same stage. Do not disable hooks. |
| OpenBao member sealed after replacement | Auto-unseal has not finished. | Wait, then rerun `check_openbao`. If it stays sealed after five minutes, follow the runbook's recovery guidance. |
| Cassandra member not `UN` | The pod is restarting or joining. | Wait for it to become Ready and rerun `nodetool status`; do not continue while any member is down. |
| The image check prints `BACKWARD` | An old image pin survived in your environment file, or you started from a release that is not covered. | Stop. Remove pins you did not set on purpose ([Decide the HA mode and prepare configuration](#decide-the-ha-mode-and-prepare-configuration)) and render again. If the component belongs to a release that is not covered, do not continue. |
| A NATS pod is not Ready after [Apply the dependency stage](#apply-the-dependency-stage) | The 1.1.4 NATS pods run as a non-root user (uid 1000), or an image could not be pulled. | Read the pod events and logs. Confirm the images pull from your registry or mirror ([Decide the HA mode and prepare configuration](#decide-the-ha-mode-and-prepare-configuration)) and that the volume is writable by group 1000. |
| Compute plane identity changed | The registration file or `NCA_ID` was wrong. | Stop. Restore the original registration file and rerun the diff before applying. |

## Rollback boundary

If an upgrade fails, stop and use your deployment's reviewed recovery
procedure. Do not apply your old packages unchanged as a blanket rollback.
Helm rollback does not reverse stored data, does not validate a database or
OpenBao downgrade, and does not revert a Cassandra replication factor you
raised. The Cassandra migrations in 1.1.4 add columns and indexes, and a rollback
does not remove them. Older services have not been tested against that schema. Restore data only through the reviewed procedure for that datastore,
using the backups from [Back up persistent state](#back-up-persistent-state). After any recovery, verify the original cluster
identities, old-image canaries, durable data and availability. Changing which
package you use does not roll back a running deployment.
