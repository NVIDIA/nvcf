# Upgrade from docs edition 1.0.2 to NVCF 1.0.4

This procedure upgrades the combination documented in docs edition 1.0.2.
The docs-only 1.0.3 edition used the same stack versions. Stack versions are
independent of the NVCF umbrella version.

| Stack | Docs edition 1.0.2 | NVCF 1.0.4 |
| --- | --- | --- |
| Self-Managed | 1.0.1 | 1.0.7 |
| Compute Plane | 1.0.0 | 1.0.4 |
| Observability | 1.0.0 | 1.0.0 |

Obtain the selected packages through [Consume an NVCF release](../umbrella-releases.md).
Use the packaged Makefiles and Helmfiles below. Keep the three stack directories
together. The [release notes](../../../fern/changelog/2026-10-26.mdx) describe
the changes; the release manifest supplied with the packages records their pins.

<Warning>
Apply the hostname policy before changing the admin issuer route. Upgrade NVCA
before changing shared worker defaults, and drain pending work before rolling
NATS. Do not run a whole-stack apply before completing those steps.
</Warning>

## Before starting

1. Retain the current configuration, Helm values, image references, database
   backups and persistent-volume snapshots. Record cluster registrations,
   function/deployment IDs, running tasks and schema versions. Keep one serving
   function, one secret-bearing workload and one running task as canaries.
1. Prepare the target environment and secrets files using the
   [customer artifact access settings](../umbrella-releases.md#configure-customer-artifact-access).
   Review carried-forward overrides. Keep the selected chart/image versions;
   do not copy old version overrides over the target defaults.
1. Retain the existing compute-plane registration file and account ID. An
   upgrade reuses that identity; do not run `register-cluster` again.
1. Use Helm 3.21.4, Helmfile 1.1.9, `kubectl`, `jq`, `curl` and Mike Farah's
   `yq` v4. The Helmfiles use the environment
   named `default`; `HELMFILE_ENV` chooses the values file. `helmfile -e <name>`
   is not the equivalent command for these packages.
1. Arrange a maintenance window and a way to stop new requests and task
   submissions. Keep the canary and availability records throughout the window.

For older source stacks, complete the
[staged upgrade to Self-Managed 1.0.1](0.6.1-to-1.0.1-upgrade.md) first.
Do not skip schema or data-backfill stops. If an earlier ICMS migration requires
its legacy instance lookup backfill, run `MIGRATE`, then `VALIDATE`, then
`DISABLED`. Validation must report no active rows with missing requests,
mismatches or failures.

## 1. Select the packages, contexts and retained identity

Run these commands in Bash and keep the same shell for the later steps.
Replace the example paths, context names and IDs with the existing deployment's
values. `REGISTRATION_VALUES_DIR` contains the retained
`<cluster-name>-register-values.yaml` file.

```bash
set -euo pipefail
umask 077
export TARGET_BUNDLE="/absolute/path/to/extracted-1.0.4"
export CONTROL_STACK="$TARGET_BUNDLE/deploy/stacks/self-managed"
export COMPUTE_STACK="$TARGET_BUNDLE/deploy/stacks/nvcf-compute-plane"
export HELMFILE_ENV="production"
export CLUSTER_NAME="existing-gpu-cluster"
export NCA_ID="existing-account-id"
export REGISTRATION_VALUES_DIR="/secure/path/to/existing-registration"
export CONTROL_SOURCE_KUBECONFIG="/secure/path/to/control-kubeconfig"
export COMPUTE_SOURCE_KUBECONFIG="/secure/path/to/compute-kubeconfig"
export CONTROL_CONTEXT="existing-control-context"
export COMPUTE_CONTEXT="existing-compute-context"
export UPGRADE_RECORD="$HOME/nvcf-upgrades/$CLUSTER_NAME-1.0.4-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$UPGRADE_RECORD"
export CONTROL_KUBECONFIG="$UPGRADE_RECORD/control.kubeconfig"
export COMPUTE_KUBECONFIG="$UPGRADE_RECORD/compute.kubeconfig"

kubectl --kubeconfig "$CONTROL_SOURCE_KUBECONFIG" --context "$CONTROL_CONTEXT" \
  config view --minify --flatten --raw > "$CONTROL_KUBECONFIG"
kubectl --kubeconfig "$COMPUTE_SOURCE_KUBECONFIG" --context "$COMPUTE_CONTEXT" \
  config view --minify --flatten --raw > "$COMPUTE_KUBECONFIG"

test -s "$CONTROL_STACK/environments/$HELMFILE_ENV.yaml"
test -s "$CONTROL_STACK/secrets/$HELMFILE_ENV-secrets.yaml"
test -s "$COMPUTE_STACK/environments/$HELMFILE_ENV.yaml"
test -s "$REGISTRATION_VALUES_DIR/$CLUSTER_NAME-register-values.yaml"
kubectl --kubeconfig "$CONTROL_KUBECONFIG" config current-context
kubectl --kubeconfig "$COMPUTE_KUBECONFIG" config current-context
kubectl --kubeconfig "$CONTROL_KUBECONFIG" get nodes
kubectl --kubeconfig "$COMPUTE_KUBECONFIG" get nodes
```

Both context names must match the intended targets and all required nodes must
be Ready. For a single-cluster deployment, both targets identify the same
cluster. The saved kubeconfigs contain credentials; keep the record private.
The control-plane Makefile has no context argument, so its kubeconfig must
select only the intended context.

These shell helpers keep the context explicit in the stage commands:

```bash
control_helmfile() {
  (cd "$CONTROL_STACK" &&
    HELMFILE_ENV="$HELMFILE_ENV" helmfile --environment default \
      --kubeconfig "$CONTROL_KUBECONFIG" "$@")
}
wait_workloads() {
  local kubeconfig="$1" namespace="$2"
  kubectl --kubeconfig "$kubeconfig" -n "$namespace" \
    get deployments,statefulsets -o name |
    while IFS= read -r workload; do
      kubectl --kubeconfig "$kubeconfig" -n "$namespace" \
        rollout status "$workload" --timeout=15m
    done
  kubectl --kubeconfig "$kubeconfig" -n "$namespace" get pods
}
record_identity() {
  kubectl --kubeconfig "$COMPUTE_KUBECONFIG" -n nvca-operator \
    get configmap nvcfbackend-self-managed -o jsonpath='{.data.cluster-dto\.yaml}' |
    yq -o=json '{"clusterId": .clusterId, "clusterGroupId": .clusterGroupId,
      "clusterName": .clusterName, "ncaID": .ncaID}' |
    jq -eS 'if all(.[]; type == "string" and length > 0)
      then . else error("Missing cluster identity") end'
}
```

## 2. Render and record the starting state

Use new output directories so the Makefiles' `clean` target cannot remove an
existing render or registration handoff.

```bash
make -C "$CONTROL_STACK" template HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$CONTROL_KUBECONFIG" OUTPUT_DIR="$UPGRADE_RECORD/control-render"
make -C "$COMPUTE_STACK" template HELMFILE_ENV="$HELMFILE_ENV" \
  CLUSTER_NAME="$CLUSTER_NAME" NCA_ID="$NCA_ID" \
  REGISTRATION_VALUES_DIR="$REGISTRATION_VALUES_DIR" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" COMPUTE_KUBE_CONTEXT="$COMPUTE_CONTEXT" \
  OUTPUT_DIR="$UPGRADE_RECORD/compute-render"
helm --kubeconfig "$CONTROL_KUBECONFIG" list -A -o json > "$UPGRADE_RECORD/control-before.json"
helm --kubeconfig "$COMPUTE_KUBECONFIG" list -A -o json > "$UPGRADE_RECORD/compute-before.json"
record_identity > "$UPGRADE_RECORD/identity-before.json"
```

Review the rendered resources before applying. Confirm the expected namespaces,
retained cluster identity and customer registry settings. The selection uses API
chart 1.27.4 with API runtime 1.18.1, operator chart 1.28.0 with NVCA 3.10.3,
Samba 1.0.9 and both collectors at 0.160.0-nv-0.2.9. Rendered files can include
secrets; do not upload them to a public issue.

Check cluster egress or mirrors for all enabled images in the render, including
the [upstream supporting images](../manifest.md#supporting-images-that-ship-from-docker-hub).
NATS server and the upgrade-receipt helper do not inherit `global.image`.
Resolve access failures before changing running releases.

## 3. Refresh the hostname policy

The target checks that the selected gateway-routes chart contains the corrected
policy. Stop on an error; do not disable admission to bypass it.

```bash
make -C "$CONTROL_STACK" apply-hostname-policy HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$CONTROL_KUBECONFIG"
control_helmfile --selector release-group=ingress status
kubectl --kubeconfig "$CONTROL_KUBECONFIG" get httproutes -A
```

The ingress release must be deployed. Existing routes and serving canaries must
still work. This step runs before the admin issuer route because the regular
core-service apply reaches that route before ingress.

## 4. Upgrade the existing compute plane

Use the retained registration and account ID on each GPU cluster. Keep the
same target environment and packaged Compute Plane 1.0.4 directory.

```bash
(cd "$COMPUTE_STACK" &&
  OUTPUT_DIR="$UPGRADE_RECORD/compute-render" helmfile --environment default \
    --kubeconfig "$COMPUTE_KUBECONFIG" --kube-context "$COMPUTE_CONTEXT" \
    diff --suppress-secrets)
```

Review the diff before continuing. The exported `HELMFILE_ENV`, `CLUSTER_NAME`
and `NCA_ID`, plus the registration file copied during render, select the
existing cluster. Then apply:

```bash
make -C "$COMPUTE_STACK" apply HELMFILE_ENV="$HELMFILE_ENV" \
  CLUSTER_NAME="$CLUSTER_NAME" NCA_ID="$NCA_ID" \
  REGISTRATION_VALUES_DIR="$REGISTRATION_VALUES_DIR" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" COMPUTE_KUBE_CONTEXT="$COMPUTE_CONTEXT" \
  OUTPUT_DIR="$UPGRADE_RECORD/compute-render"
wait_workloads "$COMPUTE_KUBECONFIG" nvca-operator
kubectl --kubeconfig "$COMPUTE_KUBECONFIG" -n nvca-system get pods
kubectl --kubeconfig "$COMPUTE_KUBECONFIG" -n nvca-operator get nvcfbackends
record_identity > "$UPGRADE_RECORD/identity-after.json"
diff -u "$UPGRADE_RECORD/identity-before.json" "$UPGRADE_RECORD/identity-after.json"
```

The operator and agent must be ready, the backend must report healthy, and the
cluster/account identity must be unchanged. Investigate any identity-file diff
before proceeding. Existing function and task canaries must still work with
their old worker images. On separate compute clusters, retain the existing
Observability 1.0.0 configuration; do not install a second copy of shared
observability resources.

## 5. Drain pending work

Stop new production requests and task submissions at their callers. Wait for
pending work in single-replica memory queues to drain before rolling NATS or
dependent services. Check every affected function/version, not just the canary.
With the configured CLI and a key that has `queue_details` scope:

```bash
NVCF_CLI="/absolute/path/to/nvcf-cli"
NVCF_CLI_CONFIG="/secure/path/to/nvcf-cli.yaml"
FUNCTION_ID="existing-function-id"
VERSION_ID="existing-version-id"
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function queue status "$FUNCTION_ID" "$VERSION_ID"
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" task list --status RUNNING
```

Queue size must reach zero for all affected queues. A missing queue response is
not proof that work drained. Record running task identities and results rather
than cancelling them to obtain an empty queue. An already-empty stream can
reset its sequence; pending-message loss is a failure.

Also inspect the control plane's single-replica memory streams on every NATS
server. Function queue status alone does not cover them. This check uses the
NATS monitoring port, 8222, through Kubernetes port-forwarding. Choose an unused
local port and keep production submissions paused:

```bash
NATS_MONITOR_PORT=18223
NATS_PODS=$(kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n nats-system \
  get pods -o json | jq -r '.items[] |
    select(any(.spec.containers[]; .name == "nats")) | .metadata.name')
test -n "$NATS_PODS"
mkdir "$UPGRADE_RECORD/nats-drain"
for pod in $NATS_PODS; do
  (
    kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n nats-system \
      port-forward --address 127.0.0.1 "pod/$pod" "$NATS_MONITOR_PORT:8222" \
      > "$UPGRADE_RECORD/nats-drain/$pod.log" 2>&1 &
    forward_pid=$!
    trap 'kill "$forward_pid" 2>/dev/null || true; wait "$forward_pid" 2>/dev/null || true' EXIT
    for attempt in {1..30}; do
      kill -0 "$forward_pid"
      if grep -q 'Forwarding from 127.0.0.1:' "$UPGRADE_RECORD/nats-drain/$pod.log"; then
        break
      fi
      sleep 1
    done
    grep -q 'Forwarding from 127.0.0.1:' "$UPGRADE_RECORD/nats-drain/$pod.log"
    curl --fail --silent --show-error \
      "http://127.0.0.1:$NATS_MONITOR_PORT/jsz?accounts=true&streams=true&config=true" \
      > "$UPGRADE_RECORD/nats-drain/$pod.json"
    jq -e '.account_details | type == "array"' "$UPGRADE_RECORD/nats-drain/$pod.json"
    jq -e 'all(.account_details[];
      (.stream_detail | type == "array") and
      all(.stream_detail[];
        (.config.storage | type == "string") and
        (.state.messages | type == "number")))' "$UPGRADE_RECORD/nats-drain/$pod.json"
  )
done
jq -se '[.[] | .account_details[]? | .stream_detail[]? |
  select(.config.storage == "memory" and (.config.num_replicas // 1) == 1) |
  {name: .name, messages: .state.messages}] |
  if length > 0 and all(.[]; .messages == 0)
  then . else error("Memory streams missing or not drained; do not roll NATS") end' \
  "$UPGRADE_RECORD/nats-drain/"*.json
```

Every observed single-replica memory stream must have zero messages. A failed
read, missing stream or nonzero count blocks the rollout. Investigate, wait
for work to drain and repeat with a new record directory; do not discard
messages to make the check pass. If monitoring is configured differently,
use its configured endpoint and retain the same per-server checks.
Check the monitoring response for pagination. If it reports more accounts or
streams than returned, retrieve all pages before accepting the drain result.

## 6. Apply control-plane stages in order

The packaged stages wait for their releases and jobs. Run one stage, check its
result and canaries, then continue. Keep new production submissions paused.
Before each stage's `apply`, run the same command with `diff --suppress-secrets`
in place of `apply` and review the result. Do not proceed with unexpected
deletions, identity changes or version overrides.

### Observability infrastructure

```bash
control_helmfile --allow-no-matching-release \
  -f helmfile.d/00-observability-infrastructure.yaml.gotmpl apply
control_helmfile --allow-no-matching-release \
  -f helmfile.d/00-observability-infrastructure.yaml.gotmpl status
```

A disabled profile has no releases. Enabled profiles reapply the unchanged
Observability 1.0.0 stack. Preserve the existing profile. Check each configured
observability namespace with `wait_workloads`; the default is `monitoring`.
Every enabled release must be deployed. Existing-backend modes must retain
their configured endpoints and data. Do not enable new profiles during this
upgrade merely because the package contains them.

### Dependencies and migrations

```bash
control_helmfile -f helmfile.d/01-dependencies.yaml.gotmpl apply
control_helmfile -f helmfile.d/01-dependencies.yaml.gotmpl status
for namespace in nats-system cert-manager vault-system cassandra-system; do
  wait_workloads "$CONTROL_KUBECONFIG" "$namespace"
  kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n "$namespace" get jobs
done
```

All selected dependency releases must be deployed and their new migration jobs
must complete successfully. Investigate failures before applying core services.
Confirm that Cassandra data and OpenBao secrets remain available; a Ready pod
alone does not prove data preservation.

### Core services

```bash
control_helmfile -f helmfile.d/02-core.yaml.gotmpl apply
control_helmfile -f helmfile.d/02-core.yaml.gotmpl status
for namespace in api-keys sis nvcf ess nats-system; do
  wait_workloads "$CONTROL_KUBECONFIG" "$namespace"
done
kubectl --kubeconfig "$CONTROL_KUBECONFIG" get httproutes -A
```

Core releases must be deployed, their workloads ready and their routes accepted.
Check any additional enabled addon namespaces from the render. Repeat the
serving-function, running-task and secret-delivery canaries before continuing.

### State metrics and autoscaling

```bash
control_helmfile --allow-no-matching-release \
  -f helmfile.d/03-observability.yaml.gotmpl apply
control_helmfile --allow-no-matching-release \
  -f helmfile.d/03-observability.yaml.gotmpl status
wait_workloads "$CONTROL_KUBECONFIG" nvcf
```

Keep the existing enablement settings. Enabled state-metrics and autoscaler
releases must be deployed and healthy. The `control` and `all` profiles require
state metrics; do not disable that dependency to bypass a failed validation.

### Upgrade receipt

Write the receipt only after every earlier stage succeeds:

```bash
control_helmfile -f helmfile.d/04-upgrade-receipt.yaml.gotmpl apply
kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n nvcf \
  get job upgrade-receipt --ignore-not-found
kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n nvcf \
  get configmap nvcf-upgrade-receipt -o yaml
test "$(kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n nvcf \
  get configmap nvcf-upgrade-receipt -o jsonpath='{.data.installed_stack_version}')" \
  = "$(cat "$CONTROL_STACK/VERSION")"
```

Helm waits for the receipt hook to succeed. The receipt must record Self-Managed
1.0.7. Its hook job is removed after ten minutes, so the ConfigMap is the
persistent record. A receipt records the applied stack version,
not the outcome of your workload checks.

## 7. Verify workloads and repeat apply

Repeat the canary invocations and compare the original function/deployment IDs,
cluster identity, running task results and persistent data. Verify initial
secret delivery and natural refresh, file ownership and permissions. Create
and invoke a new function and a new task using the deployment's normal inputs.

For a classic function canary, use its known request body and response:

```bash
CANARY_REQUEST='{"input":"your-known-canary-input"}'
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function invoke \
  --function-id "$FUNCTION_ID" --version-id "$VERSION_ID" \
  --request-body "$CANARY_REQUEST" --timeout 120
```

Use the [LLM invocation options](../cli.md#invoke-function) for an LLM
canary. Exercise API-driven worker replacement and confirm completion, state
and invocation continuity. New defaults apply when workers are replaced;
updating defaults does not replace every worker.

After these checks, repeat the control-plane apply:

```bash
make -C "$CONTROL_STACK" apply HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$CONTROL_KUBECONFIG"
control_helmfile status
```

There must be no unexpected version or configuration changes. Repeat the
workload and data checks, then resume production submissions and check queue
progress and telemetry. Keep any disruption and failure records with the
installed configuration.

## Checks for changed behavior

| Area | Check after upgrade |
| --- | --- |
| API | LLM requests sent to the unsupported classic invocation endpoint return the existing not-found response promptly. Supported classic requests and access checks still work. |
| NVCA and NATS | A new deployment or termination request is processed even if a restarted stream reuses an old transport sequence. Genuine redelivery remains idempotent. |
| NATS authentication | Authentication recovers after reconnect, and an NKey plugin does not change the account used by a subsequent plugin. The callout's `/readyz` reflects connection readiness; `/healthz` remains live while reconnecting. |
| ESS agent | A non-root secret refresh preserves an existing readable file's owner and mode with the required `CHOWN` capability. Check the actual file permissions and persistent volumes used by your workloads. |
| ICMS | Instance events and reconnection preserve deployment state. Check legacy lookup fields if the installation previously required a backfill. |
| Pylon | Queued LLM requests may wait up to 300 seconds for first output after response headers. The 30-second inter-token stall deadline remains. |
| Samba storage | Verify a non-root Helm task can create its results directory and write to the share. Samba 1.0.9 applies share ownership and permissions before starting its daemon and fails startup when that setup fails. Its daemon still uses the existing root runtime. |
| Workers and telemetry | Check NICLLS when enabled, Samba-backed storage, and both ordinary and BYOO collector paths that the deployment uses. |

NATS now defaults to upstream `docker.io/synadia/nats-server:2.14.6-alpine3.22`
with UID/GID 1000. The stack accepts server, reloader and box image overrides.
cert-manager and Vault injector overrides are also available, but do not change
their defaults automatically. Keep cert-manager components and CRDs compatible,
keep OpenBao server/agent selections paired, and record exact overrides.

## Rollback boundary

If the upgrade fails, stop and use the deployment-specific reviewed recovery
procedure. Retain patched NVCA, the corrected hostname policy and invocation
probes. Do not apply an old bundle unchanged as a blanket rollback.
Verify original identities, old-image canaries, durable data and availability
after rollback. It does not establish an old-agent downgrade or database
migration reversal. Restore durable data only through the reviewed recovery
procedure for that datastore. Changing the docs selector does not roll back a
running deployment.

Cassandra runtime remains 5.0.9-nv-2.0.5 and OpenBao server/agent remain
2.6.2-nv-1.3.4. Their migration images advance to 0.17.7 and 0.19.9 respectively.
Large runtime upgrades, state-metrics changes and a Samba non-root redesign
are outside this release.
