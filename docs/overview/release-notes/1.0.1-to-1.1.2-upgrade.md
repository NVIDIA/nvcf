# Upgrade from NVCF Self-Managed 1.0.1 to 1.1.2

This guide upgrades a running NVCF deployment from the 1.0.1 control plane to
the 1.1.2 control plane, and each GPU cluster from the 1.0 compute plane to
compute plane 1.1.0. Every step has commands you can copy and run. Read the
whole guide, including [What changes](#what-changes), before you start.

| Stack | Source | Target | Source tag |
| --- | --- | --- | --- |
| Self-Managed (control plane) | 1.0.1 | 1.1.2 | `deploy/stacks/self-managed/v1.1.2` |
| Compute Plane | 1.0.0 or later in the 1.0 train | 1.1.0 | `deploy/stacks/nvcf-compute-plane/v1.1.0` |
| Observability | 1.0.0 | 1.0.0 (unchanged) | `deploy/stacks/observability/v1.0.0` |

Compute plane 1.1.0 requires control plane 1.1.0 or later, and compute plane
1.0.0 keeps working against control plane 1.1.2 during the window between the
two upgrades. See the [compatibility matrix](../compatibility-matrix.md).
Upgrade the control plane first, then each GPU cluster.

This guide was written for 1.0.1 as the starting point. If you run another 1.0.x
patch, follow the same stages and compare your starting chart versions with the
[chart table](#what-changes) before applying each stage. Starting from 0.6.x?
Complete the [0.6.2 to 1.0.1 upgrade](./0.6.1-to-1.0.1-upgrade.md) first. Do not
skip its schema or backfill stops.

<Warning>
Do not run a whole-stack `make apply` or `helmfile sync` first. The control
plane has stops that must happen in order: hostname policy, dependencies and
migrations, OpenBao pod replacement, core services, then Cassandra replication
for high availability. Highly available (HA) mode is **on by default** in 1.1.2.
Decide your mode in [Step 3](#step-3-decide-the-ha-mode-and-prepare-configuration)
before you apply anything.
</Warning>

### Control plane: behavior that changes

| Area | What happens on upgrade | What you do |
| --- | --- | --- |
| High availability | `highAvailability.mode` is new and defaults to `preferred`. An environment file that does not set it **activates HA**: replica-safe services scale to 2, Cassandra and NATS scale to 3 members, and PodDisruptionBudgets and placement rules apply. | Choose `none`, `preferred` or `enforced` in [Step 3](#step-3-decide-the-ha-mode-and-prepare-configuration). |
| Cassandra | The chart adds a config setting (`range_request_timeout: 5000ms`). The pod template carries a config checksum, so the StatefulSet restarts its pods one at a time. The migrations image is `nvcf-cassandra-migrations:0.17.6` in both stacks, so the stack applies no new schema. | Plan a short Cassandra interruption if you run a single member. |
| OpenBao | Server image `2.6.2-nv-1.3.4` becomes `2.6.3-nv-1.3.6`, and the migrations image used by the server hooks moves from 0.19.5 to 0.23.0. The StatefulSet uses `OnDelete`, so Helm success does **not** replace the running pods. | Replace the pods yourself in [Step 9](#step-9-replace-the-openbao-pods). |
| Gateway hostname policy | The 1.0.1 gateway-routes chart (1.18.2) has an older hostname policy that blocks the new admin issuer route patch. 1.18.3 carries the corrected policy. | Run the one-time `apply-hostname-policy` step ([Step 6](#step-6-refresh-the-hostname-policy)). |
| Event Ledger | New release `event-ledger`, on by default (`addons.eventLedger.enabled: true`). It uses the existing `event_ledger` keyspace, and its OpenBao setup runs in the OpenBao migrations job. | Keep it on, or set `addons.eventLedger.enabled: false` before you apply. |
| NATS worker authentication | New `nats.workerAuth` setting. The default, `nkey`, keeps today's behavior. | Nothing, unless you switch to `token`. See "Worker NATS Authentication" in [control-plane operations](../../self-managed/control-plane-operations.md). |
| Admin issuer proxy | Now optional (`adminIssuerProxy.enabled`), still on by default. | Nothing, unless you want to disable it. |
| NVCT remote config | New `nvctApi.remoteConfig`, empty by default. | Nothing. |
| Upgrade receipt | The final stage records the installed stack version in `nvcf-upgrade-receipt`. See [Known issues](#known-issues) for the version it records. | Run the last stage. |

with; the new defaults apply to deployments created or replaced afterwards.

## Before you start

1. Schedule a maintenance window. You will pause new function invocations and
   task submissions, and a single-member Cassandra restarts once.
1. You need an operator workstation with `kubectl`, `helm` 3.12 or later,
   `helmfile` **1.1.x** (not 1.2.x), the `helm-diff` plugin 3.11 or later, `jq`,
   `curl`, Mike Farah's `yq` v4, and `ngc` if you download packages from NGC.
   Helmfile 1.2.0 removed sequential execution, which these stacks need. See
   [required tools](../../self-managed/helmfile-installation.md#required-tools-and-software).
1. Keep your existing 1.0.1 and compute-plane directories, your
   `environments/<environment-name>.yaml`, your
   `secrets/<environment-name>-secrets.yaml`, and the registration file for each
   GPU cluster (`<cluster-name>-register-values.yaml`). The upgrade reuses each
   cluster's registration. **Do not run `register-cluster` again.**
1. Choose canary workloads: one serving function, one function that reads a
   secret, and one running task. You will test them before and after.
1. If you mirror images and charts to a private registry, mirror the 1.1.2
   artifacts first. Step 2 checks availability.

## Step 1: Set up the session

Use a dedicated shell. Replace every value in angle brackets. Run this block
first, and again after any shell restart.

```bash
bash
set -euo pipefail
umask 077

export WORKDIR="$HOME/nvcf-upgrade-1.1.2"
export OLD_CONTROL_STACK="/absolute/path/to/existing/nvcf-self-managed-stack"
export OLD_COMPUTE_STACK="/absolute/path/to/existing/nvcf-compute-plane-stack"
export HELMFILE_ENV="<environment-name>"
export CONTROL_CONTEXT="<control-plane-kube-context>"
export BACKUP_DIR="$WORKDIR/backup"
mkdir -p "$WORKDIR" "$BACKUP_DIR"

# One kubeconfig per cluster, so a stray context switch cannot redirect a command.
export CONTROL_KUBECONFIG="$WORKDIR/control.kubeconfig"
kubectl config view --minify --flatten --raw --context "$CONTROL_CONTEXT" > "$CONTROL_KUBECONFIG"

kc() { kubectl --kubeconfig "$CONTROL_KUBECONFIG" "$@"; }
control_helmfile() {
  (cd "$CONTROL_STACK" && HELMFILE_ENV="$HELMFILE_ENV" \
    helmfile --environment default --kubeconfig "$CONTROL_KUBECONFIG" "$@")
}
wait_workloads() {
  local kubeconfig="$1" namespace="$2" workload strategy
  kubectl --kubeconfig "$kubeconfig" -n "$namespace" get deployments,statefulsets -o name |
    while IFS= read -r workload; do
      strategy=$(kubectl --kubeconfig "$kubeconfig" -n "$namespace" \
        get "$workload" -o jsonpath='{.spec.updateStrategy.type}')
      if [ "$strategy" = "OnDelete" ]; then
        printf '%s uses OnDelete; replace its pods with the procedure in this guide\n' "$workload"
        continue
      fi
      kubectl --kubeconfig "$kubeconfig" -n "$namespace" rollout status "$workload" --timeout=15m
    done
  kubectl --kubeconfig "$kubeconfig" -n "$namespace" get pods
}
declare -f kc control_helmfile wait_workloads > "$WORKDIR/helpers.sh"
declare -p WORKDIR OLD_CONTROL_STACK OLD_COMPUTE_STACK HELMFILE_ENV CONTROL_CONTEXT \
  BACKUP_DIR CONTROL_KUBECONFIG > "$WORKDIR/session.sh"

kc config current-context
kc get nodes
```

All nodes must be `Ready`. To resume later, start a new `bash`, run
`set -euo pipefail`, then `source "$WORKDIR/session.sh"` and
`source "$WORKDIR/helpers.sh"`. The saved kubeconfig holds credentials, so keep
`$WORKDIR` private.

## Step 3: Decide the HA mode and prepare configuration

### Choose the HA mode

| Mode | Result | Needs |
| --- | --- | --- |
| `none` | Keeps the 1.0.1 footprint: no extra replicas, no new PodDisruptionBudgets. | Nothing. |
| `preferred` (default) | Replica-safe services run 2 replicas. Cassandra, NATS and OpenBao run 3 members with soft anti-affinity and zone spread. Pods still schedule when capacity is short. | At least 3 schedulable nodes. |
| `enforced` | Same sizing with hard placement. Pods stay `Pending` rather than co-locate. | At least 3 nodes, 3 zones with capacity, `topology.kubernetes.io/zone` labels, and a `WaitForFirstConsumer` StorageClass. |

If this is a single-node cluster, or you are not ready to add capacity, choose
`none`. You can move to HA later with the same procedure. The full behavior,
including zone spread, is in the [high availability guide](../../self-managed/high-availability.md).

Check what your cluster offers:

```bash
kc get nodes -L topology.kubernetes.io/zone
kc get storageclass
kc get nodes --no-headers | wc -l
```

For `enforced`, the StorageClass your Cassandra, NATS and OpenBao volumes use
must show `WaitForFirstConsumer` as its volume binding mode. Replica-safe
services roll with `maxUnavailable: 0` and `maxSurge: 1`, so leave room for one
extra pod per service.

### Carry your settings into the new packages

The new `base.yaml` files contain the 1.1.2 defaults and chart settings. Copy
only **your own changes** into new environment files. Do not copy the whole old
file, because that would overwrite new defaults with old ones.

```bash
# Your customizations: the lines in your environment file that differ from the old base.
diff -u "$OLD_CONTROL_STACK/environments/base.yaml" \
  "$OLD_CONTROL_STACK/environments/$HELMFILE_ENV.yaml" \
  | tee "$WORKDIR/control-overrides.diff"

cp "$CONTROL_STACK/environments/base.yaml" "$CONTROL_STACK/environments/$HELMFILE_ENV.yaml"
cp "$OLD_CONTROL_STACK/secrets/$HELMFILE_ENV-secrets.yaml" \
  "$CONTROL_STACK/secrets/$HELMFILE_ENV-secrets.yaml"
```

Open `$WORKDIR/control-overrides.diff` and re-apply each `+` line in
`$CONTROL_STACK/environments/$HELMFILE_ENV.yaml`. Typical lines are your
registry and chart source (`global.helm.sources`, `global.image`), Gateway
settings, storage class and size, node selectors and `imagePullSecrets`. Do not
carry over image tag or chart version overrides unless you deliberately pin
them; the 1.1.2 defaults are the qualified set. Keep a pin for
`cassandra.migrations.image.tag` only if you already have one.

Then set the HA mode and, if you want to turn Event Ledger off, its switch. In
the environment file:

```yaml
highAvailability:
  mode: preferred   # none | preferred | enforced
addons:
  eventLedger:
    enabled: true   # set false to skip the new Event Ledger release
```

Merge these keys into the existing `addons:` section; do not duplicate it.

### Check the secrets file for replica overrides

Under `preferred` and `enforced`, the render fails if the secrets file sets a
value that conflicts with the HA sizing, for example `replicaCount: 1`. Look
for them now:

```bash
grep -nE 'replica(Count|s):' "$CONTROL_STACK/secrets/$HELMFILE_ENV-secrets.yaml" \
  || echo "no replica overrides"
```

Remove any replica override the HA sizing should control, or choose
`highAvailability.mode: none`. Record the mode you chose:

```bash
yq '.highAvailability' "$CONTROL_STACK/environments/$HELMFILE_ENV.yaml"
```

## Step 4: Check the starting state and take backups

Do not continue unless every check passes.

```bash
# Releases deployed
helm --kubeconfig "$CONTROL_KUBECONFIG" list -A -o json > "$WORKDIR/control-before.json"
jq -r '.[] | "\(.namespace)\t\(.name)\t\(.chart)\t\(.status)"' "$WORKDIR/control-before.json" | sort
test -z "$(jq -r '.[] | select(.status != "deployed") | .name' "$WORKDIR/control-before.json")" \
  && echo "all releases deployed"

# Cassandra: every member UN
for pod in $(kc -n cassandra-system get pods -l app.kubernetes.io/name=cassandra \
  -o jsonpath='{.items[*].metadata.name}'); do
  kc -n cassandra-system exec "$pod" -c cassandra -- nodetool status
  break
done

# Workloads ready everywhere
for namespace in cassandra-system nats-system vault-system nvcf api-keys ess sis; do
  kc -n "$namespace" get pods
done

# Record replica counts and images before the upgrade
kc get deploy,sts -A -o wide > "$WORKDIR/workloads-before.txt"
kc -n nvcf get configmap nvcf-upgrade-receipt -o yaml > "$WORKDIR/receipt-before.yaml" 2>/dev/null || true
```

Cassandra must report every member `UN`. The OpenBao check function used in
this guide, and again in Step 8, is:

```bash
check_openbao() {
  local pod pods
  pods=$(kc -n vault-system get pods -l app.kubernetes.io/name=openbao,component=server \
    -o jsonpath='{.items[*].metadata.name}') || return 1
  [ -n "$pods" ] || { echo "No OpenBao server pods found" >&2; return 1; }
  for pod in $pods; do
    echo "== $pod =="
    kc -n vault-system exec "$pod" -c openbao -- sh -c \
      'BAO_ADDR=http://127.0.0.1:8200 bao status -format=json' || return 1
  done
}
declare -f check_openbao >> "$WORKDIR/helpers.sh"
check_openbao
```

Every OpenBao member must be `initialized: true` and `sealed: false`, with the
same `cluster_id`. Exactly one reports `is_self: true`; standbys report
`is_self: false` or omit the field. Record the cluster ID.

Run your canary workloads now and record their results. With the configured
`nvcf-cli`:

```bash
export NVCF_CLI="/absolute/path/to/nvcf-cli"
export NVCF_CLI_CONFIG="/secure/path/to/nvcf-cli.yaml"
export FUNCTION_ID="<existing-function-id>"
export VERSION_ID="<existing-version-id>"
export CANARY_REQUEST='{"input":"your-known-canary-input"}'
declare -p NVCF_CLI NVCF_CLI_CONFIG FUNCTION_ID VERSION_ID CANARY_REQUEST >> "$WORKDIR/session.sh"

"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function invoke \

  --request-body "$CANARY_REQUEST" --timeout 120

```

### Back up persistent state

Create restorable backups before you change anything. Follow your storage
provider's procedure for volume snapshots as well; the commands below create
the application-level backups.

```bash
CASSANDRA_REPLICAS=$(kc -n cassandra-system get statefulset cassandra -o jsonpath='{.spec.replicas}')
echo "$CASSANDRA_REPLICAS" > "$BACKUP_DIR/cassandra-replicas"
for ordinal in $(seq 0 $((CASSANDRA_REPLICAS - 1))); do
  pod="cassandra-${ordinal}"
  kc -n cassandra-system exec "$pod" -c cassandra -- nodetool flush
  kc -n cassandra-system exec "$pod" -c cassandra -- nodetool snapshot -t pre-1-1-2
done
```

The Cassandra snapshot stays on each persistent volume. It is not an off-cluster
backup, so also copy or snapshot the volumes.

Take the OpenBao Raft snapshot from the **active** member. A snapshot taken from
a standby fails with `incomplete snapshot`.

```bash
OPENBAO_ACTIVE=""
for pod in $(kc -n vault-system get pods -l app.kubernetes.io/name=openbao,component=server \
  -o jsonpath='{.items[*].metadata.name}'); do
  if kc -n vault-system exec "$pod" -c openbao -- sh -c \
    'BAO_ADDR=http://127.0.0.1:8200 bao status' | grep -Eq '^HA Mode[[:space:]]+active$'; then
    OPENBAO_ACTIVE="$pod"
  fi
done
echo "active member: $OPENBAO_ACTIVE"

kc -n vault-system get secret openbao-server-root-token -o jsonpath='{.data.root_token}' | base64 -d |
  kc -n vault-system exec -i "$OPENBAO_ACTIVE" -c openbao -- sh -c \
  'read -r BAO_TOKEN; export BAO_TOKEN BAO_ADDR=http://127.0.0.1:8200; bao operator raft snapshot save /tmp/openbao-pre-1-1-2.snap'
kc -n vault-system cp -c openbao "$OPENBAO_ACTIVE:/tmp/openbao-pre-1-1-2.snap" \
  "$BACKUP_DIR/openbao-pre-1-1-2.snap"
kc -n vault-system exec "$OPENBAO_ACTIVE" -c openbao -- rm -f /tmp/openbao-pre-1-1-2.snap

# The snapshot restores only with the unseal key and root token.
kc -n vault-system get secret openbao-server-unseal -o yaml > "$BACKUP_DIR/openbao-server-unseal.yaml"
kc -n vault-system get secret openbao-server-root-token -o yaml > "$BACKUP_DIR/openbao-server-root-token.yaml"

# Helm values of every release, and your configuration files.
mkdir -p "$BACKUP_DIR/helm-values"
jq -r '.[] | "\(.namespace) \(.name)"' "$WORKDIR/control-before.json" |
  while read -r namespace release; do
    helm --kubeconfig "$CONTROL_KUBECONFIG" get values "$release" -n "$namespace" -o yaml \
      > "$BACKUP_DIR/helm-values/control-$namespace-$release.yaml"
  done
cp "$OLD_CONTROL_STACK/environments/$HELMFILE_ENV.yaml" "$BACKUP_DIR/old-environment.yaml"
cp "$OLD_CONTROL_STACK/secrets/$HELMFILE_ENV-secrets.yaml" "$BACKUP_DIR/old-secrets.yaml"
ls -l "$BACKUP_DIR"
```

The unseal and root-token files, the secrets copy and the exported values
contain credentials. Protect them like the snapshot. NVCF NATS streams use
memory storage, so a NATS backup holds stream metadata only. Do not continue
until the Cassandra and OpenBao backups exist.

## Step 5: Render and review the changes

Render into a new directory, then review the diff the first stage would apply.

```bash
make -C "$CONTROL_STACK" template HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$CONTROL_KUBECONFIG" OUTPUT_DIR="$WORKDIR/control-render"

# Images the 1.1.2 render pulls; make sure each one is in your registry or mirror.
grep -rhoE 'image:[[:space:]]*"?[A-Za-z0-9._/:@-]+' "$WORKDIR/control-render" \
  | sed -E 's/image:[[:space:]]*"?//' | sort -u
```

The render can include secrets, so keep it private. Check that the namespaces
match your cluster and that no image lacks the registry you expect.

## Step 6: Refresh the hostname policy

This is a required one-time step for upgrades from 1.0.1. The 1.0.1 gateway
routes chart installed a hostname policy that denies the admin issuer proxy
route patch, and that release applies before `ingress`. The target checks that
the pinned chart (1.18.3) carries the corrected policy and then applies only
the `ingress` release.

```bash
make -C "$CONTROL_STACK" apply-hostname-policy HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$CONTROL_KUBECONFIG"
helm --kubeconfig "$CONTROL_KUBECONFIG" -n envoy-gateway-system status ingress
kc get httproutes -A
```

The `ingress` release must be `deployed`, and your existing routes and
canaries must still work. Stop on any error; do not disable admission to get
past it. If the target reports that the pinned chart "still reserves hostnames",
the packages do not match the selected release; recheck Step 2.

## Step 7: Pause traffic and drain queues

Stop new production requests and task submissions at their callers. NATS
request queues use memory storage, and the dependency stage can restart NATS.
Wait for queued work to finish; do not cancel it to get an empty queue.

For every affected function and version, with a key that has `queue_details`
scope:

```bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function queue status "$FUNCTION_ID" "$VERSION_ID"
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" task list --status RUNNING
```

Queue sizes must reach zero. Record the identities and results of running
tasks. Then check the control plane's own single-replica memory streams on every
NATS server, through the monitoring port 8222:

```bash
NATS_MONITOR_PORT=18223
NATS_PODS=$(kc -n nats-system get pods -o json | jq -r '.items[] |
  select(any(.spec.containers[]; .name == "nats")) | .metadata.name')
test -n "$NATS_PODS"
mkdir -p "$WORKDIR/nats-drain"
for pod in $NATS_PODS; do
  (
    kc -n nats-system port-forward --address 127.0.0.1 "pod/$pod" "$NATS_MONITOR_PORT:8222" \
      > "$WORKDIR/nats-drain/$pod.log" 2>&1 &
    forward_pid=$!
    trap 'kill "$forward_pid" 2>/dev/null || true; wait "$forward_pid" 2>/dev/null || true' EXIT
    for attempt in {1..30}; do
      kill -0 "$forward_pid"
      grep -q 'Forwarding from 127.0.0.1:' "$WORKDIR/nats-drain/$pod.log" && break
      sleep 1
    done
    grep -q 'Forwarding from 127.0.0.1:' "$WORKDIR/nats-drain/$pod.log"
    curl --fail --silent --show-error \
      "http://127.0.0.1:$NATS_MONITOR_PORT/jsz?accounts=true&streams=true&config=true" \
      > "$WORKDIR/nats-drain/$pod.json"
  )
done
jq -se '[.[] | .account_details[]? | .stream_detail[]? |
  select(.config.storage == "memory" and (.config.num_replicas // 1) == 1) |
  {name: .name, messages: .state.messages}] |
  if length > 0 and all(.[]; .messages == 0)
  then . else error("Memory streams missing or not drained; do not roll NATS") end' \
  "$WORKDIR/nats-drain/"*.json
```

Every single-replica memory stream must show zero messages. A failed read, a
missing stream or a nonzero count blocks the upgrade. Wait for the work to drain
and repeat; do not discard messages. If your NATS monitoring is configured
differently, use its endpoint and keep the same per-server check.

## Step 8: Apply the dependency stage

This stage updates Cassandra, NATS, cert-manager, OpenBao and the PKI. Review
the diff first, and stop on unexpected deletions or version overrides:

```bash
control_helmfile -f helmfile.d/01-dependencies.yaml.gotmpl diff --suppress-secrets
```

Apply it:

```bash
control_helmfile -f helmfile.d/01-dependencies.yaml.gotmpl apply
control_helmfile -f helmfile.d/01-dependencies.yaml.gotmpl status
for namespace in nats-system cert-manager vault-system cassandra-system; do
  wait_workloads "$CONTROL_KUBECONFIG" "$namespace"
  kc -n "$namespace" get jobs
done
```

What you will see:

- **Cassandra** restarts one pod at a time because of the config change, and
  grows to 3 members under `preferred` or `enforced`. A single-member cluster is
  unavailable while its one pod restarts.
- **Migrations** run as Helm hook jobs. They must complete successfully. The
  Cassandra migrations image is unchanged, so they apply no new schema; the
  OpenBao hooks (image 0.23.0) refresh the service, admin issuer and Event
  Ledger configuration.
- **OpenBao** shows the new template, but its pods still run the old image
  until Step 9. `wait_workloads` reports it as `OnDelete`.

Check that the data is intact, not only that pods are Ready:

```bash
kc -n cassandra-system exec cassandra-0 -c cassandra -- nodetool status
kc -n cassandra-system get jobs
kc -n vault-system get jobs
```

All Cassandra members must be `UN` and every migration job `Complete`.
Investigate any failed job before continuing; do not disable hooks.

## Step 9: Replace the OpenBao pods

The OpenBao StatefulSet uses `OnDelete`: Helm updated its template, but the
running pods keep their old image. Replace them one at a time, standbys first.
Never delete a persistent volume claim, reinitialize OpenBao, or replace more
than one member at once. This procedure is the 2.6.2 to 2.6.3 patch procedure
from the [OpenBao patch upgrade runbook](../../self-managed/runbooks/openbao-patch-upgrade.md).
Use that runbook if a step fails or if you customized plugin registration,
policies or PKI.

Confirm the new template and the update strategy:

```bash
kc -n vault-system get statefulset openbao-server \
  -o jsonpath='{range .spec.template.spec.containers[*]}{.name}{": "}{.image}{"\n"}{end}{"updateStrategy: "}{.spec.updateStrategy.type}{"\n"}'
check_openbao
```

The server image must be `nvcf-openbao:2.6.3-nv-1.3.6` and the strategy
`OnDelete`. If either is different, stop. Identify the standbys (the members
that do not report `is_self: true`) and replace one:

```bash
POD="<standby-pod-name>"
kc -n vault-system delete pod "$POD" --wait=true --timeout=3m
kc -n vault-system wait "pod/$POD" --for=condition=Ready --timeout=5m
check_openbao
```

If the new pod has not appeared yet, wait for it before repeating the wait. The
replacement must report `version: "2.6.3"`, `sealed: false` and the original
`cluster_id`. If it is Ready but still sealed, let auto-unseal finish and run
`check_openbao` again. Repeat for the second standby only after all three
members are healthy.

Then replace the former active member. Transfer leadership first:

```bash
ACTIVE_POD="<current-active-pod-name>"
set -o pipefail
kc -n vault-system get secret openbao-server-root-token -o json |
  jq -er '.data.root_token | @base64d' |
  kc -n vault-system exec -i "$ACTIVE_POD" -c openbao -- sh -ec '
    IFS= read -r BAO_TOKEN
    test -n "$BAO_TOKEN"
    export BAO_TOKEN
    export BAO_ADDR=http://127.0.0.1:8200
    bao operator step-down
  '
check_openbao
```

Wait until a 2.6.3 member reports `is_self: true` and the old active reports
standby. A successful request alone does not confirm the transfer. Then replace
the former active with the same `delete`, `wait`, `check_openbao` sequence. Do
not enable shell tracing or print the token.

Verify all three members and their images:

```bash
check_openbao
kc -n vault-system get pods -l app.kubernetes.io/name=openbao,component=server \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{range .spec.containers[*]}{"  "}{.name}{": "}{.image}{"\n"}{end}{end}'
```

All three must be unsealed on 2.6.3, with one active member and the original
cluster ID. Updating the injector affects only new pods. The services the core
stage rolls in the next step pick up the new agent; roll any other injected
workload through its normal deployment procedure, one service at a time, and
check its authentication and rendered secrets. A single-replica service can be
interrupted during that roll, so never restart all consumers together.

## Step 12: Raise replication for HA

Skip this step if you chose `highAvailability.mode: none`.

After the dependency stage, Cassandra has 3 members, but your application
keyspaces keep the replication factor they were created with, so losing one
Cassandra node can still make data unavailable. Wait until all three Cassandra
pods are Ready, then raise each keyspace to RF=3 and repair, one member at a
time. Skip any keyspace your installation does not have; the query below lists
them.

```bash
read -rs -p "Cassandra administrator password: " CASSANDRA_PASSWORD; echo
kc -n cassandra-system exec cassandra-0 -c cassandra -- \
  cqlsh -u cassandra -p "$CASSANDRA_PASSWORD" \
  -e "SELECT keyspace_name, replication FROM system_schema.keyspaces;"

for ks in nvcf_api nvct_api ess_api api_keys_api sis_api event_ledger nvcf_autoscaler; do
  kc -n cassandra-system exec cassandra-0 -c cassandra -- \
    cqlsh -u cassandra -p "$CASSANDRA_PASSWORD" \
    -e "ALTER KEYSPACE $ks WITH replication = {'class': 'NetworkTopologyStrategy', 'ncp': '3'};"
done
for pod in cassandra-0 cassandra-1 cassandra-2; do
  kc -n cassandra-system exec "$pod" -c cassandra -- nodetool repair --full
done
unset CASSANDRA_PASSWORD
```

Until the repairs finish, reads at `LOCAL_ONE` can miss rows that exist only on
the original replica. The application keyspaces must now report `'ncp': '3'`.

JetStream streams are created with the replication factor current at creation
time. The `icms` streams raise themselves to the configured factor when it
starts. Streams created earlier by `nvcf-api` and `invocation-service` stay at
1 replica until you edit them. List them and check:

```bash
kc -n nats-system exec deploy/nats-box -- nats stream report
```

The `Replicas` column lists each member that holds a copy of the stream. A
highly available stream shows three (`nats-0`, `nats-1`, `nats-2`); a stream
created before HA shows one. Raise each stream that shows one:

```bash
STREAM="<stream-name>"
kc -n nats-system exec deploy/nats-box -- nats stream edit "$STREAM" --replicas=3 --force
kc -n nats-system exec deploy/nats-box -- nats stream info "$STREAM"
```

Replace `<stream-name>` with the name from the report, run both commands for
each such stream, and confirm `nats stream info` shows `Replicas: 3`. Use 3, not
2: a 2-replica stream loses quorum when either member is down. The NATS
commands run in the `nats-box` deployment because the `nats` server container
does not include the CLI.

## Step 15: Upgrade each compute cluster

Do this for every GPU cluster, after the control plane is verified. Use the
cluster's **existing registration**; the cluster, group and account identity must
not change.

### Set the variables

```bash
export COMPUTE_CONTEXT="<gpu-cluster-kube-context>"
export CLUSTER_NAME="<gpu-cluster-name>"
export NCA_ID="<existing-account-id>"
export REGISTRATION_VALUES_DIR="/secure/path/to/existing-registration"
export COMPUTE_KUBECONFIG="$WORKDIR/compute-$CLUSTER_NAME.kubeconfig"
kubectl config view --minify --flatten --raw --context "$COMPUTE_CONTEXT" > "$COMPUTE_KUBECONFIG"
kg() { kubectl --kubeconfig "$COMPUTE_KUBECONFIG" "$@"; }
record_identity() {
  kg -n nvca-operator get configmap nvcfbackend-self-managed \
    -o jsonpath='{.data.cluster-dto\.yaml}' |
    yq -o=json '{"clusterId": .clusterId, "clusterGroupId": .clusterGroupId,
      "clusterName": .clusterName, "ncaID": .ncaID}' |
    jq -eS 'if all(.[]; type == "string" and length > 0)
      then . else error("Missing cluster identity") end'
}
declare -p COMPUTE_CONTEXT CLUSTER_NAME NCA_ID REGISTRATION_VALUES_DIR COMPUTE_KUBECONFIG >> "$WORKDIR/session.sh"
declare -f kg record_identity >> "$WORKDIR/helpers.sh"

test -s "$REGISTRATION_VALUES_DIR/$CLUSTER_NAME-register-values.yaml"
kg get nodes
record_identity | tee "$WORKDIR/identity-before-$CLUSTER_NAME.json"
```

The registration file must exist and every node must be `Ready`. If you do not
know the cluster name or account ID, `record_identity` prints them from the
running operator; set `CLUSTER_NAME` and `NCA_ID` from its output and run the
block again. Confirm the NVCA operator is healthy before you change it:

```bash
kg -n nvca-operator get nvcfbackends
kg -n nvca-operator get pods
kg -n nvca-system get pods
```

### Carry your settings into the compute package

```bash
diff -u "$OLD_COMPUTE_STACK/environments/base.yaml" \
  "$OLD_COMPUTE_STACK/environments/$HELMFILE_ENV.yaml" \
  | tee "$WORKDIR/compute-overrides.diff"
cp "$COMPUTE_STACK/environments/base.yaml" "$COMPUTE_STACK/environments/$HELMFILE_ENV.yaml"
```

Re-apply each `+` line from `compute-overrides.diff` in
`$COMPUTE_STACK/environments/$HELMFILE_ENV.yaml` (registry, image settings,
observability profile and similar). Do not copy old `nvcaVersion`, `imageTag`
or chart pins over the 1.1.0 defaults. Leave `workerCallbackCaPem` empty unless
you serve worker callbacks over TLS with a private CA. If your clusters share
one environment file, do this once.

### Check images, render and review

```bash
make -C "$COMPUTE_STACK" template HELMFILE_ENV="$HELMFILE_ENV" \
  CLUSTER_NAME="$CLUSTER_NAME" NCA_ID="$NCA_ID" \
  REGISTRATION_VALUES_DIR="$REGISTRATION_VALUES_DIR" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" COMPUTE_KUBE_CONTEXT="$COMPUTE_CONTEXT" \
  OUTPUT_DIR="$WORKDIR/compute-render-$CLUSTER_NAME"
grep -rhoE 'image:[[:space:]]*"?[A-Za-z0-9._/:@-]+' "$WORKDIR/compute-render-$CLUSTER_NAME" \
  | sed -E 's/image:[[:space:]]*"?//' | sort -u
```

Mirror every image the list shows (NVCA 3.18.6, shared storage 1.0.9, image
credential helper 0.11.4 and the BYOO collector 0.160.0-nv-0.4.7 are new
defaults) before you apply. Then review the diff:

```bash
(cd "$COMPUTE_STACK" && HELMFILE_ENV="$HELMFILE_ENV" CLUSTER_NAME="$CLUSTER_NAME" \
  NCA_ID="$NCA_ID" OUTPUT_DIR="$WORKDIR/compute-render-$CLUSTER_NAME" \
  helmfile --environment default --kubeconfig "$COMPUTE_KUBECONFIG" \
  --kube-context "$COMPUTE_CONTEXT" diff --suppress-secrets)
```

Expect the `nvca-operator` chart to move from 1.28.0 to 1.37.1 and the NVCA
agent to 3.18.6. Stop if the diff shows the registration or cluster identity
changing, or unexpected deletions.

### Apply

```bash
make -C "$COMPUTE_STACK" apply HELMFILE_ENV="$HELMFILE_ENV" \
  CLUSTER_NAME="$CLUSTER_NAME" NCA_ID="$NCA_ID" \
  REGISTRATION_VALUES_DIR="$REGISTRATION_VALUES_DIR" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" COMPUTE_KUBE_CONTEXT="$COMPUTE_CONTEXT" \
  OUTPUT_DIR="$WORKDIR/compute-render-$CLUSTER_NAME"
wait_workloads "$COMPUTE_KUBECONFIG" nvca-operator
kg -n nvca-system get pods
kg -n nvca-operator get nvcfbackends
record_identity > "$WORKDIR/identity-after-$CLUSTER_NAME.json"
diff -u "$WORKDIR/identity-before-$CLUSTER_NAME.json" "$WORKDIR/identity-after-$CLUSTER_NAME.json" \
  && echo "cluster identity unchanged"
```

The operator and agent must be ready, the backend must report healthy, and
the identity files must match. If they differ, stop and inspect them before
doing anything else. Do not install a second copy of shared observability
resources on separate compute clusters; keep your existing 1.0.0 configuration.

Confirm from the control plane that the cluster is registered and healthy:

```bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" cluster list-registered
```

Existing function and task canaries must still work with their old worker
images. To move a function to the new worker defaults, replace its deployment
through the [deployment API or CLI](../cli.md#deploy-function); updating the
stack defaults alone does not change running workers or explicit per-function
image overrides. Plan for the interruption while a replacement rolls.

Repeat this step for each remaining GPU cluster, with its own `CLUSTER_NAME`,
`NCA_ID`, registration directory and kube context.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| Render fails with `overrides the highAvailability sizing` | The secrets file sets a replica count that conflicts with the HA sizing. | Remove the override, or set `highAvailability.mode: none`. See Step 3. |
| `ImagePullBackOff` in a stage | An image is not in your registry or mirror. | Re-run the Step 2 checks, mirror the missing image, and retry the stage. |
| Pods `Pending` under `enforced` | Fewer than 3 nodes or zones with capacity, or a StorageClass without `WaitForFirstConsumer`. | Add capacity or fix the StorageClass. `preferred` schedules them but does not give zone protection. |
| `apply-hostname-policy` reports the chart still reserves hostnames | The package does not match the selected release. | Recheck the extracted package against Step 2, then rerun. |
| The admin issuer route patch is denied | The hostname policy step was skipped. | Run Step 6, then rerun the core stage. |
| A migration job failed | A dependency was not ready, or a hook could not reach its service. | Read the job logs (`kc -n <namespace> logs job/<name>`), fix the cause, and rerun the same stage. Do not disable hooks. |
| OpenBao member sealed after replacement | Auto-unseal has not finished. | Wait, then rerun `check_openbao`. If it stays sealed after five minutes, follow the runbook's recovery guidance. |
| Cassandra member not `UN` | The pod is restarting or joining. | Wait for it to become Ready and rerun `nodetool status`; do not continue while any member is down. |
| Compute plane identity changed | The registration file or `NCA_ID` was wrong. | Stop. Restore the original registration file and rerun the diff before applying. |

## Rollback boundary

If an upgrade fails, stop and use your deployment's reviewed recovery
procedure. Do not apply the old 1.0.1 packages unchanged as a blanket rollback.
Helm rollback does not reverse stored data, does not validate a database or
OpenBao downgrade, and does not revert a Cassandra replication factor you
raised. Restore data only through the reviewed procedure for that datastore,
using the backups from Step 4. After any recovery, verify the original cluster
identities, old-image canaries, durable data and availability. Changing which
package you use does not roll back a running deployment.

## Known issues

- **The package `VERSION` file.** The 1.1.2 control-plane package's `VERSION`
  file contains `1.1.0`, and the upgrade receipt records that value. The receipt
  check in Step 13 compares the receipt with the package's own file, so it
  passes. To confirm the release you applied, rely on the chart versions and
  images in [Step 14](#step-14-verify-the-control-plane), not the receipt.
- **Starting from other 1.0.x patches.** This guide was validated against the
  1.0.1 chart pins. Compare your installed chart versions with the table in
  [What changes](#what-changes) if you started from a later 1.0 patch.
