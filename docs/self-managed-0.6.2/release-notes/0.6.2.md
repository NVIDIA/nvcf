# NVCF Self-Managed 0.6.2 Release Notes

The 0.6.2 patch refreshes OpenBao's JWT plugin catalog during an upgrade.
Upgrade in this order:

```text
0.6.1 -> 0.6.2 -> 1.0.1
```

Installations before 0.6.1 must complete the earlier documented upgrades first.
See the [patch procedure](/nvcf/overview/0-6-1-to-0-6-2-upgrade), then the
[0.6.2 to 1.0.1 procedure](/nvcf/overview/0-6-2-to-1-0-1-upgrade).

## OpenBao changes

| Component | 0.6.1 | 0.6.2 |
| --- | --- | --- |
| OpenBao chart | 0.30.25 | 0.32.6 |
| Server, injected agent, auto-unseal sidecar | 2.5.5-nv-1.3.1 | 2.5.5-nv-1.3.1 |
| OpenBao migrations | 0.16.2 | 0.16.2 |
| Injector | 1.7.4 | 1.7.4 |

The chart adds a `post-upgrade` JWT catalog refresh Job with hook weight `0`.
It calculates the plugin digest from the target server image and registers
that digest before the migrations Job, which has hook weight `1`.
Registration does not reload the plugin in running servers. The StatefulSet
uses `OnDelete`; the upgrade procedure must account for manual pod rotation.
The healthy-source candidate rehearsal needed no rotation because the server
pod template and catalog checksum already matched. Stale-catalog recovery and
custom runtime overrides still require qualification.

Explicit stack defaults retain the legacy migration and injected-agent
versions when consuming the newer chart. Existing server and migration image
overrides remain supported. Record any override in the upgrade baseline;
substituting an image changes the plugin compatibility assessment.

The candidate retains the other 0.6.1 chart pins. The
[manifest](../manifest.md) lists the resolved control-plane inventory,
including optional releases and hook images. Existing compute clusters are
outside this patch's control-plane inventory; retain their qualified versions.

## Rehearsal results

The [patch rehearsal](/nvcf/overview/0-6-1-to-0-6-2-upgrade#rehearsal-results)
confirmed hook ordering, retained runtime versions, fresh JWT issuance,
injection, data preservation, worker continuity, and repeatable Helm syncs
from a healthy 0.6.1 source. Its isolated ARM64 topology and registry
adaptations limit that result. It does not cover stale-catalog recovery,
custom runtime overrides, or production failure domains. The
[onward rehearsal](/nvcf/overview/0-6-2-to-1-0-1-upgrade#candidate-rehearsal-evidence)
retained the original workload but recorded control-plane probe failures.
