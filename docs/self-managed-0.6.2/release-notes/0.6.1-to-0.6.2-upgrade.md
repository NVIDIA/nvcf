# Upgrade from NVCF Self-Managed 0.6.1 to 0.6.2

<Warning>
Draft procedure. Stable 0.6.2 and its public bundle are not yet available.
The candidate inventory is `deploy/stacks/self-managed/v0.6.2-rc.0`.
The healthy-source candidate rehearsal passed. Stable-release qualification
and stale-catalog recovery testing remain pending. Do not execute this draft
on a production deployment.
</Warning>

The patch updates OpenBao chart 0.30.25 to 0.32.6 while retaining the 0.6.1
runtime versions. Complete this patch and validate the deployment before
following the [0.6.2 to 1.0.1 upgrade](/nvcf/overview/0-6-2-to-1-0-1-upgrade).

## Prerequisites and baseline

Start with a healthy 0.6.1 deployment. Every source Helm release must be
deployed, every OpenBao member initialized and unsealed, and every Cassandra
migration ledger clean. Resolve degraded health before changing charts.

Use the Helm 3 and Helmfile 1.1.x versions supported by the released bundle.
Set explicit paths and the intended context:

```bash
export SOURCE_CONTROL=<absolute-path-to-0.6.1-bundle>
export TARGET_CONTROL=<new-absolute-path-for-0.6.2-bundle>
export CONTROL_KUBECONFIG=<control-plane-kubeconfig>
export CONTROL_CONTEXT=<control-plane-context>
export HELMFILE_ENV=<existing-environment-name>
export BACKUP_DIR=<new-private-backup-directory>

umask 077
mkdir -p "$BACKUP_DIR"
kcp() {
  kubectl --kubeconfig "$CONTROL_KUBECONFIG" \
    --context "$CONTROL_CONTEXT" "$@"
}
test "$(kubectl --kubeconfig "$CONTROL_KUBECONFIG" config current-context)" \
  = "$CONTROL_CONTEXT"
kcp cluster-info
helm --kubeconfig "$CONTROL_KUBECONFIG" --kube-context "$CONTROL_CONTEXT" \
  list --all-namespaces > "$BACKUP_DIR/helm-releases.txt"
kcp -n vault-system get statefulset openbao-server -o yaml \
  > "$BACKUP_DIR/openbao-statefulset.yaml"
kcp -n vault-system get pods -o json > "$BACKUP_DIR/openbao-pods.json"
```

Record the source chart versions, image digests, replica counts, storage
settings, plugin catalog digest, JWT mount configuration, and injector webhook
settings. Preserve any server or migration image override. Record an existing
function, its deployment, cluster ID, worker identity, and successful
authenticated invocation. Keep a timestamped probe running during the patch.

## Back up state

Save the source environment values and secrets securely. Back up OpenBao with
its authenticated Raft snapshot command and verify the restore procedure:

```bash
# Run where the bao CLI already has the operator's authenticated connection.
bao operator raft snapshot save "$BACKUP_DIR/openbao.snap"
```

Take a Cassandra snapshot on every member using the site's backup procedure.
Retain the migration ledgers, database topology, and persistent-volume
identities with the backup. Also retain the source bundle and mirrored images
so recovery does not depend on a later registry lookup. Do not put tokens,
unseal material, or rendered secrets into shared logs.

## Review the rendered change

Render into a new private directory and inspect the diff:

```bash
cd "$TARGET_CONTROL"
HELMFILE_ENV="$HELMFILE_ENV" helmfile --environment default \
  --kubeconfig "$CONTROL_KUBECONFIG" --selector name=openbao-server \
  template > "$BACKUP_DIR/openbao-target.yaml"
HELMFILE_ENV="$HELMFILE_ENV" helmfile --environment default \
  --kubeconfig "$CONTROL_KUBECONFIG" --selector name=openbao-server \
  diff --suppress-secrets
```

Require chart 0.32.6; server, injected agent, and unseal sidecar
`2.5.5-nv-1.3.1`; migrations `0.16.2`; and injector `1.7.4`, unless the recorded
source deployment has an intentional override. Confirm the StatefulSet keeps
`OnDelete` and that the refresh Job precedes migrations. Inspect all changed
RBAC, hooks, webhook configuration, probes, and pod templates. Stop on an
unexpected volume, identity, runtime image, or credential change.

## Upgrade OpenBao

Both releases use migration
image 0.16.2, so observing that image tag alone cannot identify a new migration
Job. Record the old Job UID before the upgrade:

```bash
old_migration_uid=$(kcp -n vault-system get job openbao-server-migrations \
  -o jsonpath='{.metadata.uid}' --ignore-not-found)
```

In terminal 1, run the released bundle's selector-based command:

```bash
make -C "$TARGET_CONTROL" install \
  HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$CONTROL_KUBECONFIG" \
  HELMFILE_SELECTOR=name=openbao-server
```

In terminal 2, observe the new hook Jobs and their logs. Expected ordering:

1. `openbao-server-refresh-jwt-plugin-catalog` runs from the retained server
   image and registers the plugin digest. Successful refresh Jobs can be
   deleted by Helm; capture their completion while the sync runs.
2. A new `openbao-server-migrations` Job appears after refresh succeeds.
   Require a different UID from `$old_migration_uid`.
3. If the source catalog checksum is correct and the rendered server pod
   template is unchanged, wait for migrations without rotating servers. This
   path passed the candidate rehearsal. A stale catalog or a changed runtime
   or pod template requires separate recovery qualification; do not assume
   this result covers that case. When rotating, handle one server at a time,
   standbys first and the active member last. Never delete the StatefulSet,
   persistent-volume claims, or multiple members together. A single-member
   deployment has downtime during rotation.
4. Require the new migrations Job and Helm sync to complete successfully.

For each server selected for rotation, record its old UID and use:

```bash
export POD=<one-standby-pod>
old_pod_uid=$(kcp -n vault-system get pod "$POD" -o jsonpath='{.metadata.uid}')
kcp -n vault-system delete pod "$POD" --wait=true
kcp -n vault-system wait "pod/$POD" --for=condition=Ready --timeout=10m
kcp -n vault-system get pod "$POD" -o jsonpath='{.metadata.uid}{"\n"}'
kcp -n vault-system exec "$POD" -c openbao -- sh -c \
  'BAO_ADDR=http://127.0.0.1:8200 bao status'
```

Require a new pod UID, `Initialized true`, `Sealed false`, the expected image,
and healthy Raft membership before rotating another member. Readiness alone
does not prove auto-unseal has finished. Re-evaluate the active member before
the last rotation. Stop immediately if a member fails to recover.

```bash
kcp -n vault-system wait job/openbao-server-migrations \
  --for=condition=Complete --timeout=15m
helm --kubeconfig "$CONTROL_KUBECONFIG" --kube-context "$CONTROL_CONTEXT" \
  status openbao-server -n vault-system
```

## Validate and finish

Require all OpenBao members healthy and unsealed, the expected catalog digest,
and a new successful migration Job. Exercise the existing JWT-backed
authentication flow and repeat the original authenticated function invocation.
Confirm the original function, deployment, cluster, and database records still
exist. Check the injector with a new test workload in its configured webhook
scope; require successful admission and secret injection.

Inspect a full stack diff. Apply remaining expected changes only after the
OpenBao checks pass, using the bundle's normal `make install` command. Repeat
the selected OpenBao sync to test hook idempotency, then repeat health, JWT,
and injector checks. Capture probe failures separately from final recovery.

The final source for the onward upgrade must be stable 0.6.2 with all these
checks passing. Retain its values and backups as the new source baseline for
the [1.0.1 procedure](/nvcf/overview/0-6-2-to-1-0-1-upgrade).

## Candidate rehearsal evidence

The released 0.6.1 bundle was upgraded to candidate commit
`55803ad7cb647de45cf29415cfd3766225534617` on an isolated ARM64 k3d cluster.
The test used three OpenBao members, one Cassandra member, and a fake-GPU
compute pool on one Docker host. Optional add-ons and observability were
disabled. Registry transport and local resource settings were adapted for
the test; this was not a production-topology qualification.

The refresh Job completed before the new migration Job started. The server
pod template and runtime images were unchanged, and all three OpenBao members
kept their pod identities without rotation. Fresh JWT issuance, a newly
injected workload, the full stack sync, and repeated selected and full syncs
passed. Existing credentials, PVCs, function and deployment records, and
clean Cassandra ledgers were preserved. The original worker kept its pod UID,
container IDs, and restart counts.

The patch observation window recorded 218 successful checks each for function
reads, deployment reads, and authenticated invocation, with no failed checks.
This covers the tested healthy-source candidate path only. It does not prove
stale-catalog recovery, backup restoration, optional-component upgrades, or
the availability of every required public artifact.

## Stop and recovery

Stop on a failed refresh or migration, sealed member, dirty schema ledger,
JWT failure, injector failure, missing durable record, or unexpected identity
change. Retain Helm history and hook logs before retrying. Do not skip hooks
to force a successful release status.

Before any state change, the original deployment and bundle remain the
recovery baseline. After a hook changes OpenBao state, a Helm chart rollback
alone is not a complete recovery plan. Validate the catalog and runtime
combination before retrying, or restore the coordinated backup using the
site's tested restore procedure. Preserve all persistent volumes and original
credentials. Recovery and retry checkpoints remain part of the outstanding
live qualification.
