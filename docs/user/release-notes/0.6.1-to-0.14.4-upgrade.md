# 0.6.1 to 0.14.4 Upgrade

Use this procedure to upgrade a self-managed NVCF deployment directly from
control-plane stack 0.6.1 to 0.14.4.

This upgrade has two required operator checkpoints:

1. Upgrade Cassandra and verify all schema migration ledgers.
2. Upgrade OpenBao and verify its idempotent migration job.

After both checkpoints pass, sync the complete control-plane stack, refresh
each GPU cluster registration, and sync the 0.14.4 compute-plane stack.

Do not scale down the NVCF API. The API and the other function-serving
control-plane services can remain available while the Cassandra and OpenBao
hooks run. Temporarily quiesce only the NVCT API before the Cassandra hook.
The 0.6.1 NVCT runtime maps a legacy column that the target migration removes.
Function worker pods remain running throughout the procedure.

<Warning>
Plan a maintenance window. A single-replica control plane can briefly reject
API and invocation requests while the API, invocation service, and gRPC proxy
roll during the final Helmfile sync. This is a rolling replacement, not an
operator-initiated NVCF API shutdown. Existing function worker pods do not
need to be replaced, but clients must retry transient failures. Use a
supported highly available control-plane topology if uninterrupted request
handling is required.
</Warning>

<Warning>
The Cassandra migration removes deprecated autoscaler tables and deprecated
NVCT health schema. An in-place rollback to 0.6.1 is not supported after Stop 1.
Take and verify backups before starting. Roll back by restoring the 0.6.1
control plane and its Cassandra and OpenBao backups.
</Warning>

## Upgrade boundaries

The 0.6.1 to 0.14.4 path was checked for database hooks and service-owned
scheduled migrations.

| Boundary | Change | Required stop | Interim manual pin |
|---|---|---|---|
| Cassandra | Chart 0.18.0 to 0.20.3; migrations 0.10.3 to 0.17.3 | Stop 1; quiesce only NVCT API | None. Use the 0.14.4 stack pin. |
| OpenBao | Chart 0.30.25 to 0.32.4; migrations 0.16.2 to 0.19.1 | Stop 2 | None. Use the 0.14.4 stack pin. |
| NATS | Chart 0.7.1 to 0.8.1; server remains 2.11.10 | Verify streams after the full sync | None. |
| NVCF API | Chart 1.23.9 to 1.25.6; runtime 1.9.0-hotfix.1 to 1.16.4 | No service shutdown; rolling update during full sync | None. |
| NVCT API | Chart 1.4.3 to 1.5.3; runtime 1.5.9-hotfix.1 to 1.65.0 | Stop 1; source runtime uses the removed `health_info` column | None. Restore after the full sync. |
| SIS/ICMS | Chart 1.18.8 to 2.1.0; runtime 1.563.1-hotfix.1 to 1.2.2 | No service migration stop | None. |
| NVCA | Operator chart 1.12.7 to 1.22.2; NVCA 3.0.3 to 3.5.2 | Refresh registration after the control plane | None. |

The SIS auth-client-id scheduled migration in the 0.5.x to 0.6.0 procedure is
already complete in a valid 0.6.1 source deployment. Do not repeat the old SIS
1.561.1 pin. The 0.6.1 SIS runtime no longer contains that migration task.

The NVCF API runtimes at the source, intervening stack boundaries, and target
were inspected for disappearing migration tasks. None were found. The SIS
runtime contains the GPU v5 population task at both endpoints, disabled by
default. It does not create an upgrade stop.

The exact 0.6.1 NVCT runtime maps `tasks_v2.health_info` and its
`health_udt` type. Cassandra migrations 4 through 6 add the replacement
`health` column, remove `health_info`, and remove `health_udt`. Quiescing only
NVCT prevents the old runtime from issuing incompatible reads or writes after
the column is removed. No other 0.6.1 stack service uses that schema.

The 0.6.1 stack does not install function-autoscaler. If an operator added an
out-of-band autoscaler that uses the three deprecated function-history tables,
stop and remove that unsupported override before Stop 1. The 0.14.4
function-autoscaler is installed later by the full sync and uses the target
schema.

### Cassandra migration inventory

The 0.17.3 hook applies the following changes to a 0.6.1 database.

| Ledger | 0.6.1 version | 0.14.4 version | Change |
|---|---:|---:|---|
| api_keys_api | 3 | 3 | No schema change. |
| ess_api | 8 | 8 | No schema change. |
| event_ledger | Absent | 3 | Create the keyspace, role, and event tables. |
| nvcf_api | 7 | 8 | Add LLM configuration fields. |
| nvcf_autoscaler | 3 | 4 | Drop three deprecated function-history tables. The 0.6.1 stack has no consumer. |
| nvct_api | 3 | 6 | Add `health`, then remove `health_info` and `health_udt`. This is the NVCT-only hard stop. |
| sis_api | 6 | 9 | Add deployment and GPU specification IDs, indexes, and the reservation backup flag. |

The function definition table and function deployment table are not dropped or
rewritten by these migrations.

### OpenBao migration inventory

The 0.19.1 hook replays migrations 01 through 21 idempotently and adds
migration 22 for the event ledger. Existing key-value secrets are retained.
The hook also refreshes JWT roles, policies, and service registration data for
the 0.14.4 services.

## Prerequisites

- The deployed control-plane stack is 0.6.1 and is healthy.
- The 0.5.x to 0.6.0 upgrade stops, including the SIS auth-client-id migration,
  were completed before the source deployment reached 0.6.1.
- The 0.14.4 control-plane bundle, its matching compute-plane bundle, and all
  artifacts in the 0.14.4 manifest are mirrored and available.
- Helmfile 1.1.x, Helm 3.x, the Helm diff plugin, and the nvcf-cli version from
  the 0.14.4 manifest are installed.
- You have control-plane and GPU-cluster kubeconfigs and know the context for
  each cluster.
- Cassandra, OpenBao, and NATS backups have been copied outside the cluster and
  tested.

<Warning>
Use Helmfile 1.1.x. Helmfile 1.2.0 and later process files under helmfile.d in
parallel and do not preserve the ordering expected by this stack.
</Warning>

<Warning>
For a private registry, create a self-contained kubernetes.io/dockerconfigjson
Secret in every namespace used by NVCF. Do not build this Secret by copying a
Docker config that contains only credsStore or credHelpers. Kubernetes nodes
cannot call the workstation credential helper and image pulls fail with 403 or
ImagePullBackOff.
</Warning>

The following example creates the registry Secret without depending on a local
Docker credential helper:

~~~bash
for ns in \
  cassandra-system nats-system nvcf api-keys ess sis vault-system \
  nvca-operator nvca-system nvcf-backend cert-manager; do
  kubectl --context "$CONTROL_PLANE_CONTEXT" \
    create namespace "$ns" --dry-run=client -o yaml | \
    kubectl --context "$CONTROL_PLANE_CONTEXT" apply -f -

  kubectl --context "$CONTROL_PLANE_CONTEXT" \
    create secret docker-registry nvcr-pull-secret \
    --docker-server=<registry> \
    --docker-username='<user>' \
    --docker-password='<password>' \
    --namespace="$ns" \
    --dry-run=client -o yaml | \
    kubectl --context "$CONTROL_PLANE_CONTEXT" apply -f -
done
~~~

For a split deployment, create the compute-plane namespace Secrets against the
GPU-cluster context instead.

## Prepare the 0.14.4 configuration

Download and extract new 0.14.4 bundles. Do not modify or sync the 0.6.1 bundle
in place.

Set paths and cluster information for the maintenance window:

~~~bash
export HELMFILE_ENV=<environment-name>
export CONTROL_PLANE_STACK=<absolute-path-to-0.14.4-control-plane-stack>
export COMPUTE_PLANE_STACK=<absolute-path-to-matching-compute-plane-stack>
export CONTROL_PLANE_KUBECONFIG=<absolute-path-to-control-plane-kubeconfig>
export COMPUTE_KUBECONFIG=<absolute-path-to-gpu-cluster-kubeconfig>
export CONTROL_PLANE_CONTEXT=<control-plane-context>
export COMPUTE_KUBE_CONTEXT=<gpu-cluster-context>
export CLUSTER_NAME=<registered-gpu-cluster-name>
export CLUSTER_REGION=<registered-gpu-cluster-region>
export NVCF_CLI=<absolute-path-to-0.14.4-nvcf-cli>
export NVCF_CLI_CONFIG=<absolute-path-to-nvcf-cli-config>
~~~

For a single-cluster deployment, CONTROL_PLANE_KUBECONFIG and
COMPUTE_KUBECONFIG can point to the same file, and both context variables can
name the same context.

Start with the environment and secrets templates included in 0.14.4. Reconcile
the required site values from 0.6.1 into:

- environments/$HELMFILE_ENV.yaml
- secrets/$HELMFILE_ENV-secrets.yaml

Preserve the existing values for:

- Cassandra superuser and application-role credentials.
- OpenBao unseal and root material managed by the installation.
- Cassandra storage class and storage size.
- NATS and OpenBao persistent storage.
- Registry, repository, pull-secret, endpoint, domain, TLS, and issuer
  settings.
- NCA, cluster, and region identity.

Do not replace the 0.14.4 files wholesale with the 0.6.1 files. Fields and
defaults changed between these releases.

### Remove old manual pins

Remove site overrides for stack-managed chart or service tags unless NVIDIA
support gave you a separate pin specifically for 0.14.4. In particular, remove
any temporary SIS 1.561.1 pin left from the 0.5.x to 0.6.0 procedure.

Do not add intermediate pins for this upgrade. The required migration pins are
already part of 0.14.4:

- Cassandra chart 0.20.3 and migration image 0.17.3.
- OpenBao chart 0.32.4 and migration image 0.19.1.
- SIS chart 2.1.0 and ICMS runtime 1.2.2.
- NVCF API chart 1.25.6 and runtime 1.16.4.
- NVCA operator chart 1.22.2 and NVCA 3.5.2.

<Warning>
Keep the live Cassandra volume claim template unchanged. Do not use this
upgrade to change its storage class or size. Kubernetes treats those
StatefulSet fields as immutable.
</Warning>

Record the live values and compare them with the rendered 0.14.4 StatefulSet:

~~~bash
CASSANDRA_VOLUME_TEMPLATE_JSONPATH='{range .spec.volumeClaimTemplates[*]}'\
'{.metadata.name}{": storageClass="}{.spec.storageClassName}'\
'{", size="}{.spec.resources.requests.storage}{"\n"}{end}'

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n cassandra-system get statefulset cassandra \
  -o jsonpath="$CASSANDRA_VOLUME_TEMPLATE_JSONPATH"

cd "$CONTROL_PLANE_STACK"
make template \
  HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$CONTROL_PLANE_KUBECONFIG"
~~~

Do not continue if templating fails or the rendered storage settings differ
from the live StatefulSet.

## Create the pre-upgrade checkpoint

Confirm all source releases and pods are healthy:

~~~bash
helm --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --kube-context "$CONTROL_PLANE_CONTEXT" list -A

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" get pods -A

kubectl --kubeconfig "$COMPUTE_KUBECONFIG" \
  --context "$COMPUTE_KUBE_CONTEXT" \
  get nvcfbackends -n nvca-operator
~~~

Confirm that the source stack has no out-of-band function autoscaler:

~~~bash
kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n nvcf get deployment function-autoscaler --ignore-not-found
~~~

The command must return no deployment. Stop and contact NVIDIA support if a
function autoscaler was added outside the 0.6.1 stack.

List nonterminal NVCT tasks before the maintenance window:

~~~bash
for status in QUEUED LAUNCHED RUNNING; do
  "$NVCF_CLI" --config "$NVCF_CLI_CONFIG" --json task list \
    --status "$status" --limit 50
done
~~~

Allow these tasks to reach a terminal state, or cancel them according to your
site policy. The NVCT-only hard stop pauses task creation, status updates, and
task coordination until the full sync completes. It does not stop deployed
functions or their worker pods.

Record the Cassandra migration ledgers. Every existing row must have dirty set
to false:

~~~sql
SELECT table_name
FROM system_schema.tables
WHERE keyspace_name = 'schema_migrations';

SELECT version, dirty FROM schema_migrations.api_keys_api;
SELECT version, dirty FROM schema_migrations.ess_api;
SELECT version, dirty FROM schema_migrations.nvcf_api;
SELECT version, dirty FROM schema_migrations.nvcf_autoscaler;
SELECT version, dirty FROM schema_migrations.nvct_api;
SELECT version, dirty FROM schema_migrations.sis_api;
~~~

Flush and snapshot Cassandra, then copy the snapshots off-cluster:

~~~bash
kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n cassandra-system exec cassandra-0 -c cassandra -- nodetool flush

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n cassandra-system exec cassandra-0 -c cassandra -- \
  nodetool snapshot -t pre-0-14-4
~~~

Create equivalent OpenBao and NATS backups with your platform backup
procedure. Record NATS stream names before the sync:

~~~bash
kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n nats-system exec deployment/nats-box -- \
  nats stream ls --json > pre-0-14-4-nats-streams.json
~~~

### Record a function and active deployment

Choose at least one active function that can be invoked during validation:

~~~bash
export VALIDATION_FUNCTION_ID=<function-id>
export VALIDATION_VERSION_ID=<function-version-id>

"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" --json function get \
  --function-id "$VALIDATION_FUNCTION_ID" \
  --version-id "$VALIDATION_VERSION_ID" \
  > pre-0-14-4-function.json

"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function invoke \
  --request-body '{"message":"pre-upgrade","repeats":1}' \
  --timeout 120 \
  --poll-duration 5
~~~

Record the worker pod name, UID, creation time, deployment ID, container IDs,
and restart counts on the GPU cluster:

~~~bash
kubectl --kubeconfig "$COMPUTE_KUBECONFIG" \
  --context "$COMPUTE_KUBE_CONTEXT" \
  -n nvcf-backend get pods \
  -l "function-id=$VALIDATION_FUNCTION_ID" -o json | \
  jq '{
    pods: [
      .items[] | {
        name: .metadata.name,
        uid: .metadata.uid,
        created: .metadata.creationTimestamp,
        deploymentID: .metadata.labels["nvcf.nvidia.io/deployment-id"],
        containers: [
          .status.containerStatuses[] |
          {name, ready, restartCount, containerID, imageID}
        ]
      }
    ]
  }' > pre-0-14-4-worker.json
~~~

Optionally record the source database rows. The following queries use the
function-version primary key:

~~~sql
SELECT function_version_id, function_id, function_name, function_status,
       nca_id, container_image, created_at
FROM nvcf_api.functions_v3
WHERE function_version_id = <function-version-id>;

SELECT function_version_id, function_id, deployment_id, nca_id,
       created_at, last_updated_at
FROM nvcf_api.functions_deployment_v2
WHERE function_version_id = <function-version-id>;
~~~

Record each existing GPU cluster ID and cluster group ID from its current
registration values. The refresh after the control-plane sync must return the
same IDs.

## Stop 1: Cassandra schema migration

Keep the NVCF API and all other function-serving control-plane deployments
running. Record the current NVCT replica count, then quiesce only NVCT. This
starts the task API maintenance window. Function worker pods run in the
nvcf-backend namespace and are not scaled by these commands.

~~~bash
export NVCT_REPLICAS="$(
  kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
    --context "$CONTROL_PLANE_CONTEXT" \
    -n nvcf get deployment nvct-api \
    -o jsonpath='{.spec.replicas}'
)"

test "$NVCT_REPLICAS" -gt 0

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n nvcf scale deployment/nvct-api --replicas=0

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n nvcf rollout status deployment/nvct-api --timeout=5m
~~~

Do not scale down the NVCF API, invocation service, gRPC proxy, API key
service, ESS, SIS, NATS, or OpenBao. Do not scale down any deployment in the
nvcf-backend namespace.

Sync only Cassandra from the 0.14.4 control-plane stack:

~~~bash
cd "$CONTROL_PLANE_STACK"
make install \
  HELMFILE_ENV="$HELMFILE_ENV" \
  HELMFILE_SELECTOR=name=cassandra \
  KUBECONFIG_FILE="$CONTROL_PLANE_KUBECONFIG"
~~~

The command runs the migration image as a Helm post-upgrade hook and must return
zero. Verify the job:

~~~bash
kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n cassandra-system get job cassandra-migrations

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n cassandra-system logs job/cassandra-migrations
~~~

The job must report 1/1 completions and end with:

~~~text
All Cassandra migrations completed successfully
~~~

Query every ledger again. Expected versions are:

~~~text
api_keys_api     3  false
ess_api          8  false
event_ledger     3  false
nvcf_api         8  false
nvcf_autoscaler  4  false
nvct_api         6  false
sis_api          9  false
~~~

Confirm the recorded function and deployment rows still contain their original
IDs and creation timestamps. Confirm the selected worker pod retains its UID
and has not restarted.

Invoke the selected function before proceeding. It must still return
fulfilled while NVCT is quiesced:

~~~bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function invoke \
  --request-body '{"message":"after-cassandra","repeats":1}' \
  --timeout 120 \
  --poll-duration 5
~~~

Do not continue if:

- The make command or migration job failed.
- A ledger is absent, has the wrong version, or is dirty.
- The recorded function or deployment row is absent or changed unexpectedly.
- Cassandra is not healthy.

Do not uninstall Cassandra or delete its PersistentVolumeClaims while
recovering from a failed stop.

## Stop 2: OpenBao migration

Keep only NVCT quiesced. Leave the NVCF API and all other control-plane
services running. Sync only OpenBao:

~~~bash
cd "$CONTROL_PLANE_STACK"
make install \
  HELMFILE_ENV="$HELMFILE_ENV" \
  HELMFILE_SELECTOR=name=openbao-server \
  KUBECONFIG_FILE="$CONTROL_PLANE_KUBECONFIG"
~~~

Verify the 0.19.1 migration job and the three OpenBao server pods:

~~~bash
kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n vault-system get job openbao-server-migrations

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n vault-system logs job/openbao-server-migrations

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n vault-system get pods
~~~

The job must report 1/1 completions. Its log must report successful completion
for migrations 01 through 22 and end with:

~~~text
All migrations and addons completed
~~~

Do not continue if the job failed, an OpenBao server is not ready, or OpenBao
is sealed.

Invoke the selected function again. It must return fulfilled before the full
sync:

~~~bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function invoke \
  --request-body '{"message":"after-openbao","repeats":1}' \
  --timeout 120 \
  --poll-duration 5
~~~

## Sync the complete 0.14.4 control plane

Run the unscoped sync only after both migration checkpoints pass:

~~~bash
cd "$CONTROL_PLANE_STACK"
make install \
  HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$CONTROL_PLANE_KUBECONFIG"
~~~

The full sync re-runs the Cassandra and OpenBao hooks. They are idempotent. The
Cassandra log should report no change for all seven ledgers, and the OpenBao
log should again report successful completion of migrations 01 through 22.

Restore NVCT to its recorded replica count. Run this command even if Helm
already restored the replicas, because Helm can preserve a manual scale value
when the desired replica count did not change between release manifests:

~~~bash
test "$NVCT_REPLICAS" -gt 0

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n nvcf scale deployment/nvct-api --replicas="$NVCT_REPLICAS"
~~~

Wait for every chart-managed control-plane deployment to recover:

~~~bash
for ns in nvcf api-keys ess sis nats-system; do
  kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
    --context "$CONTROL_PLANE_CONTEXT" \
    -n "$ns" rollout status deployment --all --timeout=15m
done

helm --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --kube-context "$CONTROL_PLANE_CONTEXT" list -A

kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" get pods -A
~~~

All expected releases must be deployed. Running service pods must be ready.
Completed migration and initialization pods can remain in Succeeded state.

Verify that the pre-upgrade NATS streams still exist:

~~~bash
kubectl --kubeconfig "$CONTROL_PLANE_KUBECONFIG" \
  --context "$CONTROL_PLANE_CONTEXT" \
  -n nats-system exec deployment/nats-box -- \
  nats stream ls --json > post-0-14-4-nats-streams.json

diff -u pre-0-14-4-nats-streams.json post-0-14-4-nats-streams.json
~~~

Active request streams can be added or removed during normal operation. Review
any difference and confirm that expected global and active function streams
remain.

## Refresh and sync each compute plane

Repeat this section for every registered GPU cluster.

Export a new control-plane profile from the installed 0.14.4 stack:

~~~bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" self-hosted \
  --control-plane-stack "$CONTROL_PLANE_STACK" \
  --env "$HELMFILE_ENV" \
  --control-plane-context "$CONTROL_PLANE_CONTEXT" \
  --compute-plane-context "$COMPUTE_KUBE_CONTEXT" \
  control-plane profile export \
  --cluster-name "$CLUSTER_NAME" \
  --region "$CLUSTER_REGION"

"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" init
~~~

For a single-cluster deployment, omit both context flags if the selected
kubeconfig context already points to that cluster.

Refresh the existing cluster registration:

~~~bash
cd "$COMPUTE_PLANE_STACK"
make register-cluster \
  CLUSTER_NAME="$CLUSTER_NAME" \
  CLUSTER_REGION="$CLUSTER_REGION" \
  CONTROL_PLANE_PROFILE="$CONTROL_PLANE_STACK/out/control-plane-profile.yaml" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" \
  COMPUTE_KUBE_CONTEXT="$COMPUTE_KUBE_CONTEXT" \
  NVCF_CLI="$NVCF_CLI" \
  NVCF_CLI_CONFIG="$NVCF_CLI_CONFIG"
~~~

Inspect registration/$CLUSTER_NAME-register-values.yaml. The clusterID and
clusterGroupID must match the values recorded before the upgrade. Stop before
installing NVCA if either identity changed.

Render and sync the compute plane:

~~~bash
make template \
  CLUSTER_NAME="$CLUSTER_NAME" \
  HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" \
  COMPUTE_KUBE_CONTEXT="$COMPUTE_KUBE_CONTEXT" \
  NVCF_CLI="$NVCF_CLI"

make install \
  CLUSTER_NAME="$CLUSTER_NAME" \
  HELMFILE_ENV="$HELMFILE_ENV" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" \
  COMPUTE_KUBE_CONTEXT="$COMPUTE_KUBE_CONTEXT" \
  NVCF_CLI="$NVCF_CLI"
~~~

Verify NVCA:

~~~bash
kubectl --kubeconfig "$COMPUTE_KUBECONFIG" \
  --context "$COMPUTE_KUBE_CONTEXT" \
  -n nvca-operator rollout status deployment/nvca-operator --timeout=10m

kubectl --kubeconfig "$COMPUTE_KUBECONFIG" \
  --context "$COMPUTE_KUBE_CONTEXT" \
  -n nvca-operator wait nvcfbackend "$CLUSTER_NAME" \
  --for=jsonpath='{.status.agentStatus}'=healthy \
  --timeout=10m

kubectl --kubeconfig "$COMPUTE_KUBECONFIG" \
  --context "$COMPUTE_KUBE_CONTEXT" \
  -n nvca-operator get nvcfbackend "$CLUSTER_NAME" \
  -o jsonpath='{.spec.version}{" "}{.status.version}{" "}{.status.agentStatus}{"\n"}'
~~~

The expected output is:

~~~text
3.5.2 3.5.2 healthy
~~~

## Verify function and deployment preservation

Fetch the same function and compare it with the source checkpoint:

~~~bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" --json function get \
  --function-id "$VALIDATION_FUNCTION_ID" \
  --version-id "$VALIDATION_VERSION_ID" \

diff -u pre-0-14-4-function.json post-0-14-4-function.json

be unchanged.

  }' > post-0-14-4-worker.json

diff -u pre-0-14-4-worker.json post-0-14-4-worker.json
~~~

For a no-disruption result, the pod UID, deployment ID, container IDs, and
restart counts must be unchanged and every container must be ready.

Query the function and deployment rows again. They must match the source rows.
Finally, invoke the same function:

~~~bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function invoke \
  --request-body '{"message":"post-upgrade","repeats":1}' \
  --timeout 120 \
  --poll-duration 5
~~~

The invocation must finish with status fulfilled. The maintenance window can
end after all functions, deployments, cluster identities, migration ledgers,
NATS streams, and service health checks pass.

## Failure and rollback handling

- Stop at the first failed checkpoint. Do not continue to the full sync or
  compute-plane update.
- Do not uninstall Cassandra or OpenBao and do not delete their
  PersistentVolumeClaims.
- Keep NVCT quiesced after Stop 1 until either the 0.14.4 NVCT deployment is
  healthy or the verified 0.6.1 Cassandra backup has been restored.
- If Stop 1 has not changed the schema, correct the configuration or artifact
  issue and retry the selector-scoped sync.
- If Stop 1 changed the schema, restore the verified 0.6.1 Cassandra and
  OpenBao backups before restoring 0.6.1 services.
- If the control plane is healthy but compute registration or NVCA fails, keep
  the preserved cluster IDs, correct connectivity or credentials, and retry
  registration and the compute-plane sync.
